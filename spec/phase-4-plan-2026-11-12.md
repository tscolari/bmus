# BMUS Phase 4: Hardening

## Context

`spec/initial-plan-2026-10-16.md` §9 scopes Phase 4 as: a native API transporter with restricted egress and egress hails; a reconcile workflow; per-order token and turn budgets; console hardening; nightly backups; scoped permissions per division if Beams supports them. Exit: a security review of the console and Regulations, and a chaos run in holodeck (random beam loss, sleep, cert expiry) with zero lost orders.

Phase 3 has landed, the tracker interface with it, and the README ticks every Phase 3 line. Nothing for Phase 4 is filed yet, and this plan files nothing either: tickets come later. Campaigns (`spec/campaigns-plan-2026-11-03.md`) runs on its own track. This plan touches it in two places, each named where it comes up: budgets on review orders, and the routing rule that keeps some categories with the captain.

Earlier phases left some of the groundwork in place:

- `beams` already has `region`, `egress_mode`, `allowed_domains` and `compute_status` (`internal/store/schema.sql`), all unused. Today, the logic that records a new beam stores its alias as the UUID too (see `BeamRecord`, which `provisionBeam` writes), and the comment there says providers "identify beams by alias only".
- `orders.budget_tokens`, `order.create`'s `budget_tokens` and `OrderBody.BudgetTokens` carry a token budget to the beam, and `ErrorBody.Code` documents `budget_exceeded`. Nothing enforces any of it (decisions log, "SDK harness").
- A report carries token usage. Today, the logic that builds the sdk harness's report sums input (cache reads and writes included) and output tokens over the result's `modelUsage` (see `usageOf`, which `run` calls once the query ends). There is no turn count. A parked query sends no result, so a parked order's report counts only the resumed query (decisions log, "Hail parking").
- `go.mod` has no Teleport module. Every beam call shells out to `tsh` (`internal/transporter/tsh.go`).
- The console's accepted limitations were recorded for this review (decisions log, "Console address and flags"), and so were the Regulations' known gaps ("Regulations obfuscations", "Regulations gaps", "Regex `$'` noise").

### What the public Beams API offers

Read from `api/proto/teleport/beams/v1` and `tool/tsh/common` in the public `gravitational/teleport` repository at 1283425b (August 2026, the commit the decisions log's "tsh login expiry" entry read):

- `CreateBeamRequest` takes `egress` (`EGRESS_MODE_RESTRICTED` or `_UNRESTRICTED`), `allowed_domains` (restricted only), `proxy_region` and `override_region`. It carries no labels, and it blocks until the beam accepts SSH.
- `UpdateBeam` is conditional on the beam's revision. It can change `spec.allowed_domains`, `spec.publish` and metadata labels outside the `teleport.internal/beam/` prefix. `spec.egress` and `spec.expires` are immutable.
- `ListBeams` pages, and filters only by user. Visibility is governed by the `beam_labels` and `beam_labels_expression` role options.
- `GetBeam` takes the UUID name or the alias. `BeamStatus` carries `compute_status` and a `delegation_session_id`.
- `tsh beams add` hard-codes `EGRESS_MODE_UNRESTRICTED` and has no label flag. `tsh beams ls --format=json` prints `uuid` beside `id`, and its own comment says aliases are reused eventually.
- `api/client.Client` has `BeamServiceClient()`, and `client.LoadProfile(dir, name)` builds credentials from a tsh profile. The `api` module is Apache-2.0 and the repository root, `lib/` included, is AGPL-3.0. `api/go.mod` declares `go 1.26.7`; bmus declares 1.26.0.

Two of these differ from `spec/initial-plan-2026-10-16.md` §2: labels can't be set at creation, and listing can't filter on them. §3 and §5 below are built around that. Everything else about real beams in this plan is an assumption until spike S5 (§2) runs.

## Approach

### 1. Schema

New columns go into `schema.sql` and `addedColumns`, so an existing database opens unchanged. `workflowVersion` stays `"1"`.

- `beams` gains `removed_at TIMESTAMP` and `labels TEXT NOT NULL DEFAULT '{}'`. `uuid` holds the provider's real UUID from now on; rows from before keep the alias there, which reconcile (§5) reads as "UUID unknown".
- `orders` gains `budget_turns INTEGER NOT NULL DEFAULT 0` and `budget_extended INTEGER NOT NULL DEFAULT 0`, the number of extensions granted (§6).
- New table `order_usage (order_id, beam, input_tokens, output_tokens, turns, seq, PRIMARY KEY (order_id, beam))`. One row per beam that ran the order. An order's usage is the sum over its rows.
- New table `order_egress (order_id, domain, hail_id, PRIMARY KEY (order_id, domain))`: domains allowed for an order through egress hails (§4).
- New table `backups (id, started_at, finished_at, dir, bytes, error)`, written by the backup workflow (§7).

### 2. Spike S5 first

Phase 0's S5, "Beams API from Go", never ran. It goes first, on a real tenant, and its write-up (`spec/spike-beams-api-<date>.md`) decides whether §3 and §4 are built as written. A throwaway program, kept out of the repo the way the delegation spike's was, answers:

1. Does `client.LoadProfile` on the captain's tsh profile reach `BeamService` with no other setup, and does the profile's certificate expiry match `tsh status`'s `valid_until`?
2. Does a beam made by `CreateBeam` behave like one from `tsh beams add` for `tsh beams exec`, `scp`, `beamctl` and inference?
3. With restricted egress and an empty `allowed_domains`, does combadge start and does `claude` reach the LLM proxy? Which domains does the sdk harness need, if any?
4. Does `UpdateBeam` adding a domain take effect inside a running beam, and how long does it take?
5. Do labels set by `UpdateBeam` survive and come back on `ListBeams` and `GetBeam`?

If question 2 or 3 fails, §3 and §4 wait, the tsh transporter stays the only real one, and the rest of this plan proceeds unchanged.

### 3. Native API transporter

A new `internal/transporter/api.go` holds `API`, a `Provider` that calls `BeamService` for the control plane and keeps an embedded `*Tsh` for everything that runs over SSH. Beam lifecycle moves to the API: `Create`, `Remove` (`DeleteBeam` by UUID), `Exists` and the listing half of `Probe` (`GetBeam`). `Exec`, `AttachCombadge`, `StartCombadge`, `CopyTo`, `CopyFrom`, `Size` and the `beamctl list` half of `Probe` stay on tsh.

Keeping tsh for SSH is the licensing answer from `spec/initial-plan-2026-10-16.md` §2. The SSH client lives in `lib/`, which is AGPL, and only the `api` module is Apache-2.0. bmus imports `github.com/gravitational/teleport/api` and nothing else from that repository, and a CI check (`go list -deps ./... | grep teleport/lib` must print nothing) keeps it so. The go directive moves to whatever `api/go.mod` requires.

Auth comes from the captain's tsh profile: `client.LoadProfile("", "")`, the current profile under `~/.tsh`, the same login every tsh call uses. The tsh login gate (decisions log, "tsh login expiry") stays. `API.LoginValidUntil` reads the profile certificate's `NotAfter` instead of running `tsh status`, and every API call checks it first and returns `ErrLoginExpired` the way `Tsh` does. The gRPC client is rebuilt when the profile's certificate changes on disk, which is how a `tsh login` reaches it.

`Provider.Create` takes a spec:

```go
type CreateSpec struct {
    Labels map[string]string
    Egress Egress
}
type Egress struct {
    Restricted bool
    Domains    []string // FQDNs; only with Restricted
}
Create(ctx context.Context, spec CreateSpec) (Beam, error)
```

`Beam` gains `UUID`. Two methods join the interface:

- `UpdateEgress(ctx, beam Beam, domains []string) error` sets the beam's whole allowlist. `API` reads the beam, sets `allowed_domains` and calls `UpdateBeam` with the revision it read, re-reading once on a revision conflict.
- `List(ctx) ([]BeamInfo, error)`, where `BeamInfo` is `{Beam, Labels, ComputeStatus}`, lists the captain's own beams.

`Tsh` returns `transporter.ErrUnsupported` from `UpdateEgress` and from `Create` with `Restricted` set, ignores labels, and lists with `tsh beams ls`, now parsing `uuid` too. `Holodeck` writes the spec to `<beam>/beam.json` and reads it back for `List`, so tests can see what a beam was given.

`API.Create` calls `CreateBeam`, then `UpdateBeam` with the labels. The provisioning step records the beam (`InsertBeam`) right after `Create` returns, as today. A crash between `CreateBeam` and the label write leaves a beam neither the store nor reconcile can attribute; it lives out its TTL (§Assumptions).

`bmus bridge run --transporter api` selects it. `tsh` stays the default and the fallback (Open questions, 1). Setting `restricted: true` in the roster (§4) with `--transporter tsh` fails startup with a message naming `--transporter api`.

### 4. Restricted egress and egress hails

The roster gains egress per division and a base list for all of them:

```yaml
egress:
  base: []                  # every restricted beam gets these
divisions:
  ops:
    egress:
      restricted: true
      domains: [proxy.golang.org, sum.golang.org, registry.npmjs.org]
  science:
    egress:
      restricted: true
      domains: [pkg.go.dev]
```

`CheckRoster` refuses wildcards, IP addresses, schemes, ports and anything that fails IDNA ASCII conversion, and lowercases the rest. A division without `egress` stays unrestricted, as every beam is today. The provisioning step passes `Egress{Restricted, base + division + order_egress grants}` and labels (§5) to `Create`, and writes `egress_mode` and `allowed_domains` on the beam's row.

An agent asks for a domain with a new combadge tool, `request_egress({domain, reason})`, pre-allowed for every role. It becomes a hail of a new category, `comms.CategoryEgress` (`egress`), with options `[allow, deny]` and context `{domain, reason}`. Like `tracker_comment`, its hail never parks: the agent is waiting on a network call. The bridge builds the question itself, "Allow <crew>'s beam to reach <domain> for ORD-0001: <reason on one line, cut to 2 KiB>", with `oneLine`.

In the hail workflow, `classifyHail` runs a new `checkEgressRequest` before the `regs.yaml` check, as it does for splits and tracker requests. It decides by policy at once when:

- the domain is malformed (deny, with why);
- the beam's egress is unrestricted (allow, "this beam's egress is unrestricted");
- the domain is already on the beam's list (allow, "already allowed").

Anything else routes through Regulations. The default `regs.yaml` appends `- category: egress` to `captain_only`, after `tracker_comment`, so earlier indexes keep their numbers. `auto_allow` today accepts only `tool_approval` rules (`CheckRegs`). It now also accepts `category: egress` rules with a `domain` field: an exact FQDN, or `.example.com` for any name under it. No regex: a domain match that over-matches widens egress, and fail closed means exact names. `on_timeout: default_option` never decides an egress hail; it holds instead, as it does for any captain-only hail.

An allow runs one mission step between `decide-hail` and `send-answer`, `egress-update`, in the shape `create-children` and `tracker-request` use. It calls `UpdateEgress` with the beam's full list plus the domain, then writes the `order_egress` row and the beam's new list in one transaction. A re-run finds the row and calls nothing, and a re-run after a crash between the two adds a domain already there, which changes nothing. A failed `UpdateEgress` (beam gone, login expired past the step's login wait) answers deny with the error and records nothing. The answer's decision reads "allowed <domain> on <beam>".

A grant belongs to the order. Every later beam that runs the order (watch change, re-energize, a recalled order resumed elsewhere) is created with it. I think the order is the right scope: a domain one task needed says little about the next task, and widening a division is a roster edit the captain makes on purpose. `bmus order egress <id>` lists an order's grants. `HailView` needs nothing new.

Out of scope: revoking a grant mid-order, egress for Command's consult lane (it has no tools), and publishing port 8080.

### 5. Reconcile

Beams the bridge creates through `API` carry three labels: `bmus/bridge=<install id>`, `bmus/crew=<crew id>` and `bmus/tour=<tour no>`. The install id is the database's nonce (`store.Nonce`, kept in `settings` for the tracker's idempotency markers). A restored backup (§7) keeps it, and a fresh database gets a new one.

A new workflow, `reconcileWorkflow` (registered as `"reconcile"`, `internal/bridge/reconcile.go`), runs one pass:

1. Step `list-beams`: `transporter.List`. A login-expired or failed listing ends the pass with nothing done, logged once per failure streak.
2. Step `read-records`: every `beams` row with `removed_at IS NULL`, every crew member's `current_beam`, status and tour, and the ids of PENDING `transporter` workflows (`dbos.ListWorkflows`).
3. Classify each beam:
   - known: it is some crew member's `current_beam`, or its row's tour is a provisioning transporter workflow still PENDING;
   - orphan: listed, and either labelled with this bridge's install id and unknown, or a `beams` row whose crew member has since moved to another beam or been dismissed (a `removeBeam` that failed and left it to its TTL);
   - ghost: a crew member on deck, away or hailing whose `current_beam` isn't listed;
   - foreign: listed with no `bmus/bridge` label of ours and no row. Never touched.
4. Step `reap`: an orphan seen on two passes in a row, and older than 10 minutes, is removed through `removeBeam`, logging "beam <alias> reaped: <why>" (kind `beam`), and its row gets `removed_at`.
5. Ghosts get no state change from reconcile. It calls a new `Pump.ProbeNow`, which runs the same heartbeat-stale probe the pump runs on its own; a gone beam then takes the existing `heartbeat_missed` path to sickbay (`lostToSickbay`). A ghost with no pump (bridge restart) gets one from `EnsurePump` first. One path decides sickbay, and reconcile only shortens the time to it.

Rows are matched by UUID where the row has one, and by alias otherwise, since aliases get reused. `removeBeam` and `DismissCrew` set `removed_at`.

It runs once at startup, after `attachCrewTours`, and then every 5 minutes on a DBOS schedule (`dbos.ApplySchedules`, in DBOS v1.7.0). Each pass is its own workflow, `reconcile/<scheduled time>`. CLI: `bmus beams list` (each beam with its classification) and `bmus beams reconcile [--dry-run]`. RPC: `beams.list`, `beams.reconcile`. `bmus status` adds a yellow reason while a ghost or an unreaped orphan is outstanding past one pass.

With `--transporter tsh` there are no labels, and reconcile can only find orphans through `beams` rows. A beam created by a crash between `Create` and `InsertBeam` stays invisible on tsh.

### 6. Budgets

Budgets are measured on the beam and enforced there, with the bridge as the ledger and the backstop.

**Configuration.** Each division in the roster gains `budget: {tokens, turns}`. The order file and `order.create` gain `budget_turns` beside `budget_tokens`. An order's own value wins, then its division's, then none; zero means unlimited. `split_order` children and campaign orders take their division's. `resolveBudget(order, crew)` sits beside `resolveModel` in `roster.go` and returns the source the same way. `OrderBody` gains `BudgetTurns`, and both fields carry the order's current limit: the resolved budget times `1 + budget_extended`, 0 meaning unlimited. `UsedTokens` and `UsedTurns` carry the usage recorded on the order's other beams. The harness is over budget when used plus its own count for the order passes the limit; its count already holds this beam's earlier runs.

**Measuring.** The sdk harness counts as the query streams. Each main-loop `assistant` message adds its `message.usage` (input, cache read, cache creation, output) and one turn. A subagent's messages add tokens and no turns. At each `result` the harness replaces its running token count for that query with `usageOf(result)`, which also counts what the stream didn't show. Counts survive a park, which closes the gap hail parking left. A new beam-to-bridge message, `usage` (`{input_tokens, output_tokens, turns}`, cumulative for the order on this beam), goes out every 10 turns and at every checkpoint, stop and report. Like `progress`, it goes straight to the store: the pump upserts `order_usage` for (order, beam), keeping the row with the highest seq. Holodeck scripts gain a `usage` step so tests can drive it; echo reports nothing.

**Enforcing.** The harness checks the budget in its PreToolUse hook, before any other rule. Over budget, the hook asks, and `canUseTool` raises a `budget` hail (`comms.CategoryBudget`), options `[extend, stop]`, context `{used, limit, turns_used, turns_limit}`. The agent is held at its next tool call, which is the earliest point the SDK lets the harness pause it. A turn with no tool call ends the query anyway. The bridge writes the question ("ORD-0001 has used 1.2M of 1M tokens and 140 of 150 turns. Extend by its budget again, or stop?").

`budget` is captain-only in routing, whatever `regs.yaml` says, the way `campaign_land` is in the campaigns plan, and `default_option` never decides it. Spending more inference is the captain's call. On `extend`, a mission step `budget-extend` increments `budget_extended` (keyed by the hail), and the answer carries the new limit; the harness raises its limit and lets the call through. On `stop`, the harness denies the call and takes the stop path `stopRequest` uses for a stand-down: the agent commits and checkpoints, the checkpoint is pulled into the cargo bay, and the run ends with `error{code: budget_exceeded}`. The mission settles the order failed with that code. A captain who wants the work continued issues a new order from the checkpoint's branch.

The bridge backstop covers a harness that doesn't enforce, or misreports. When recorded usage passes 125% of the order's current budget, the pump's `usage` handler sends the mission a synthetic `belay` with reason "budget ceiling passed", through the path `BelayOrder` uses. A pump cannot apply a belay to the wrong order, since the usage row names it.

**Surfaces.** `OrderView` gains `budget_tokens`, `budget_turns`, `budget_source` and `usage {input_tokens, output_tokens, turns}`. `bmus order list` gains a USAGE column (`420k/1M`, `-` without a budget). `bmus order budget <id> [--tokens N] [--turns N]` changes an open order's budget, and its RPC is `order.budget`. A change reaches a running beam only with the next order send, and the captain answers the next `budget` hail with it in place. The console shows usage against budget on the away-missions card.

Command's consult lane spends tokens outside any order and isn't counted here. Neither is the per-tenant inference cap, which bmus can't read.

### 7. Backups

A new workflow, `backupWorkflow` (`"backup"`, `internal/bridge/backup.go`), writes one directory, `<backup dir>/<UTC timestamp>/`, created 0700:

- `bridge.db`: `VACUUM INTO` on a dedicated read connection. It reads one consistent snapshot of the domain tables and DBOS's tables together, holds no write lock, and compacts. I'd pick it over the online backup API, whose stepped copy starts over whenever another connection writes, and DBOS writes every few seconds. The file is checked with `PRAGMA integrity_check` before the backup counts.
- `repos/<name>.bundle`: `git bundle create` over `refs/heads/bmus/*` of each registered clone. Upstream history can be fetched again; unpushed work can't.
- `cargo/`: the cargo bay directories of orders still open (pool, directed, away, hailing, split, or parked), hard-linked when the backup dir is on the same filesystem and copied otherwise. Those are what a resume needs. A finished order's work is already in its bundle.
- `manifest.json`: the bridge version, install id, last log id, and each file's size and SHA-256.

`bmus bridge run --backup-dir <path>`, default `<home>/backups`. A backup on the same disk only guards against corruption and mistakes. The README says to point it at another disk or a synced folder. Retention keeps the newest 7 complete backups and deletes older ones after a new one passes its check.

Schedule: daily at `backup.at` in the roster (local time, default `03:00`) through a DBOS schedule. The laptop is often asleep then, so startup also runs a backup when the newest complete one is over 24 hours old. `bmus status` shows a yellow reason when the newest is over 48 hours old or the last attempt failed. CLI: `bmus backup run`, `bmus backup list`. RPC: `backup.run`, `backup.list`.

Restore is offline. `bmus backup restore <dir>` takes the bridge lock and refuses while a bridge runs. It verifies the manifest, moves `bridge.db`, `-wal` and `-shm` aside to `bridge.db.pre-restore-<timestamp>`, copies the snapshot in, fetches each bundle's `bmus/*` refs into its clone, and copies the cargo back. The next `bmus bridge run` resumes the snapshot's PENDING workflows, and reconcile then finds the beams created after the snapshot. Anything a beam sent and the bridge acked after the snapshot is gone: combadge trimmed it from its outbox. Restore prints that window ("events after <ts> are lost; check orders away at that time").

### 8. Console hardening

The console already has Host, Origin, session and CSRF checks, and the push action from #4: force offered only after a 409, behind a second confirm naming each remote; registered URLs redacted (`redactURL`) before they reach the page; and every action that runs past its deadline answered 504 `timeout`. Each item below closes a finding in the code or in the decisions log's "Console address and flags" entry.

- **CSRF on every API request.** Today, the logic that guards the API checks the CSRF header on mutations only (see `requireCSRF`, which `routes` puts on every `/api/` path). Cookies ignore ports: a local service on another 127.0.0.1 port receives the session cookie and with it can read `/api/state` and the event stream. Requiring `X-BMUS-CSRF` on every `/api/` request except `POST /api/session` makes the cookie alone useless. `EventSource` can't send headers. `web/src/feed.ts` moves to `fetch` with a streamed body, parsing the same SSE format and sending `Last-Event-ID` itself.
- **One-time launch codes.** Today, `bmus console` reads the console token from `<home>/console.token` and passes the URL with it to `xdg-open` or `open`, readable in the process list, and the token makes sessions until the bridge restarts. `bmus console` instead asks the daemon over the RPC socket (`console.launch`, already peer-credential checked) for a code that works once, within 60 seconds. `POST /api/session` takes either the code or the file's token. The token file stays for scripted use.
- **Session lifetime.** Sessions end after 12 hours idle or 7 days from creation, and on `POST /api/session/logout`. Today they live until the 64-session cap evicts them.
- **Timeouts.** The server has only `ReadHeaderTimeout`. It gains `ReadTimeout` 30s, `IdleTimeout` 120s and `MaxHeaderBytes` 16 KiB. Event streams keep their per-write deadline.
- **Rate limits.** Failed `POST /api/session` attempts: 10 a minute for the whole server. Actions: 20 a second per session. Open event streams: 4 per session, the oldest closed past that.
- **Headers.** CSP gains `frame-ancestors 'none'; base-uri 'none'; form-action 'none'; object-src 'none'`. Responses gain `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin` and a `Permissions-Policy` that turns off camera, microphone, geolocation and payment.

Tests: a handler test per rule with the exact status, including a GET with a valid cookie and no CSRF header (403), a reused launch code (401), an expired session (401), and the 11th failed session attempt (429). The existing Playwright suite, push included, runs against the fetch-based feed.

### 9. Scoped permissions per division (gated)

Beams doesn't support this yet. The delegation spike (`spec/spike-tbot-delegation-2026-10-26.md`) found that a delegated identity carries all of the captain's roles. The public API matches: `CreateBeamRequest` has no field to narrow what a beam's identity may do, and `beam_labels` role options only decide which beams a user can see. Nothing here is built.

Revisit when the API can create a beam whose delegated identity is narrower than the captain's, and a beam so narrowed still reaches inference. The design then is a roster field per division (`permissions: <scope>`) passed to `CreateSpec`, with Science read-only, Operations on staging and Command with no infrastructure access (`spec/initial-plan-2026-10-16.md` §8). Until then the captain runs the bridge as a low-privilege Teleport user, as §8 already says.

### 10. Chaos harness

The chaos run is a Go test behind a build tag, `cmd/bmus/chaos_test.go` (`//go:build chaos`), driving the real `bmus` binary and holodeck beams the way `exit_criteria_test.go` does. A test drives it, so CI can run it and a failure leaves a test log. Fault injection lives in `internal/chaos`, which the test imports; nothing ships in the binary.

Holodeck gains what it lacks for this:

- A login gate. `HolodeckConfig.LoginFile` (`bmus bridge run --holodeck-login-file`) names a file holding a `valid_until` timestamp. Holodeck then answers `LoginValidUntil` from it and fails every call but an established session with `ErrLoginExpired` once it passes, as `Tsh` does.
- `Holodeck.Vanish(alias)`: the beam's serve is killed and its directory removed, so `Exists` and `List` say gone. `Kill` already covers a beam that exists with serve dead.
- `Holodeck.CutAttach(alias)`: kills the attach process only, a network flap.

One run, seeded by `CHAOS_SEED` (printed at the start), sets up six crew in two divisions with standing orders on, the default `regs.yaml`, budgets on half the orders, and a holodeck `Lifetime` of 20 minutes so every crew member changes the watch. It feeds 60 orders over the run, scripted with progress, a hail, checkpoints, `usage` steps and a report. Answers come from a goroutine standing in for the captain. For 30 minutes it injects, at random intervals:

- beam loss: `Vanish` or `Kill` on a random live beam;
- laptop sleep: `SIGSTOP` the bridge for 30 seconds to 5 minutes, then `SIGCONT`, while beams keep running;
- login expiry: move `valid_until` into the past for 1 to 10 minutes, then forward;
- bridge crash: `SIGKILL` and restart;
- network flap: `CutAttach`;
- in-beam crash: the script's `crash` step (exit 137).

Then it stops injecting, re-energizes anything in sickbay, and waits up to 15 minutes for the ship to settle.

"Zero lost orders" means, at the end:

1. every order is in a terminal state;
2. every order is done, except those the test itself belayed, withdrew or stopped on budget, each of which ends in the state the test asked for;
3. every done order's `bmus/<order>` holds the commits its script made, and its done entry appears once;
4. every hail is decided exactly once, and every beam received each answer once (the holodeck step log);
5. no workflow is in ERROR, no mission is PENDING, and each crew member who isn't dismissed has exactly one PENDING tour;
6. after a reconcile pass, the beams that exist are exactly the crew members' current beams.

A failure prints the seed and the faults injected, in order.

It runs nightly in CI, as a new scheduled job in `.github/workflows/ci.yml` with a 60-minute timeout, and on demand with `make chaos` (`CHAOS_SEED`, `CHAOS_DURATION`). It isn't in the PR workflow: 45 minutes is too long there. The exit criterion is three nightly runs in a row with zero lost orders, plus one run under the load harness from "SQLITE_BUSY under load" (#101).

### 11. Security review

Scope: `internal/console`, `web/src`, the console half of `internal/bridge/console.go`, `internal/regs` with the default `regs.yaml`, and the hail routing that applies it (`classifyHail`, `regs.Config.Classify`, `regs.Config.CheckAnswer`). It also covers the egress and budget categories from §4 and §6.

Console checklist:

- token generation, storage (0600, removed at start and close), the launch code's single use and expiry;
- session cookie flags, lifetime, eviction, logout;
- Host checks on every path, Origin on every request that carries one and every mutation;
- CSRF on every API request, compared in constant time;
- body limits, content type, strict decoding, unknown fields;
- the shipped push endpoint: force only after a 409 and its second confirm, `redactURL` on every URL the page sees (`TestRedactURL`'s forms and any it misses), git's output kept out of every response, and the 60s deadline's `timeout` answer when a push may have landed in part;
- server timeouts, write deadlines, stream and rate limits under a flood;
- every response header in §8, checked on the 404, the missing-build page and the event stream;
- agent text rendered as text everywhere, including the new budget and egress questions;
- whatever another local user or a browser tab on another origin can reach.

Regulations checklist:

- `TestNeverAutoAnswered` and `FuzzClassify` cover each new category;
- `budget` and `campaign_land` stay captain-only whatever `regs.yaml` says;
- `default_option` can't decide a captain-only, egress or budget hail;
- egress `auto_allow` domain rules match exact names and subdomains only;
- each known gap left by the "Regulations obfuscations", "Regulations gaps" and "Regex `$'` noise" entries is either closed (§12) or accepted with its reason in the review.

The reviewer is someone, a person or a fresh agent session, who wrote none of the console or Regulations code. The review is written to `spec/security-review-<date>.md` with one row per checklist item: pass, fixed (with the change), or accepted (with why). It is done when every row has one of the three and every "fixed" has landed. The captain signs off on the accepted rows.

### 12. Candidate follow-ups

Smaller items that fit this phase. Each is a candidate, picked up if time allows.

- **A `crew:` section in `roster.yaml`.** Each entry (`id`, `name`, `division`, `harness`, `model`) whose id isn't in the store is added through `AddCrew` at startup, logged "crew <id> added from the roster". It only adds: an existing crew member is never changed, and a dismissed one isn't revived (logged once). A roster that would pass `max_beams` fails startup.
- **A split child whose division has no crew.** `checkSplit` keeps accepting it, and `splitQuestion` appends "(no crew in <division>)" to that child. Refusing would block a split the captain plans to staff, and the captain sees the note before allowing.
- **Regulations gaps cheap to close.** `git reflog expire`, `git update-ref -d` and `git worktree remove --force` join the destructive git command rules, and a Write or Edit to a path under `.git/` is tagged `external_effect`. Globs in arguments, interpreters and build tools, and settings outside the command stay accepted gaps for the review to confirm.

Split integration (stacked children, `after`, review orders) belongs to Campaigns stages 1 and 3.

## Open questions

1. **Should `api` become the default transporter?** I'd switch the default after S5 passes and a week of real orders runs clean on it, keeping `--transporter tsh`.
2. **Should a budget stop fail the order or park it?** Parking would let `bmus order budget` resume it in place, but parking is tied to recall and the pool today. I'd keep §6's failure and revisit if captains keep re-issuing stopped orders.
3. **Should Command's consults have a budget?** A runaway consult loop spends with no order to charge. I'd add a daily consult cap per bridge in a later phase, once §6's usage data shows what consults cost.
4. **Which domains go in `egress.base` by default?** It depends on S5's question 3. I'd ship it empty, with the README listing what the sdk harness turned out to need.
5. **Should backups leave the machine?** I'd keep bmus writing to a local directory and leave copying it elsewhere to the captain's own tools; an upload adds credentials the bridge doesn't otherwise hold.
6. **Should the chaos smoke run on PRs?** A 3-minute version with one fault of each kind would catch regressions a day earlier. I'd start nightly only and add the smoke if nightly failures trace back to PRs that a short run would have caught.

## Assumptions

- Everything about real beams under the API path (inference with restricted egress, `UpdateBeam` latency, labels) is unverified until S5.
- `client.LoadProfile` reads the same profile `tsh` writes, and a renewed `tsh login` replaces the certificate file in place.

- A beam created by `CreateBeam` whose label write never happened, because the bridge crashed in between, lives out its 24-hour TTL against the tenant cap. A beam from `tsh beams add` that crashed before `InsertBeam` does the same, as it does today.
- The 125% ceiling, the 10-turn usage cadence, the 5-minute reconcile interval and the 7-backup retention are starting points.
- DBOS schedules don't fire while the laptop sleeps; the startup and staleness checks in §7 cover a missed nightly run.

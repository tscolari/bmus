# BMUS Phase 2: Fleet and console

## Context

`spec/initial-plan-2026-10-16.md` §9 scopes Phase 2 as roster config; pool, divisions, priorities and the standing-orders dispatcher; transporter queue limits; checkpoints into the cargo bay and re-energize-with-resume; watch change before TTL; recall, withdraw, re-route; the console wired to live data with SSE and notifications; bridge-side push of returned bundles. Exit: six crew run real tasks for a full day, each survives at least one TTL rotation, and the console matches the mock's behaviour.

Phase 1 is complete (`spec/phase-1-plan-2026-10-16.md`). The epic #55 already has 12 sub-issues. #71-#78 implement `spec/console-plan-2026-10-18.md`, which this plan does not re-derive. #22, #48, #59 and #65 are smaller items against Phase 1 code that this plan schedules and, for #22 and #48, decides. Nothing filed so far covers roster config, the dispatcher, the transporter queue, watch change, re-energize, recall, belay, withdraw, route or push, and #59 and #78 wait on that work.

Two findings shape the design:

1. The tbot spike (`spec/spike-tbot-bridge-identity-2026-10-18.md`) is about the TTL of the bridge's own `tsh` login. Watch change is about each beam's 24h purge (D5). Every `tsh` call keeps running under the captain's session, as in Phase 1.
2. No Phase 0 write-up resolves cross-beam Claude session resume (§9's S3). Resume uses D5's fallback, "resume from handover note + diff, which is lossy but robust": a fresh Claude session on the latest checkpoint's repo state, with its handover note in the order. Nothing here depends on S3.

## Approach

### 1. Schema

Bridge databases made before the first release are disposable (`spec/phase-1-decisions-2026-10-16.md`). These changes go straight into `internal/store/schema.sql`'s `CREATE TABLE` statements, and `workflowVersion` stays `"1"`.

- `inbox` gains `tour_no`, keyed `(crew_id, tour_no, seq)` (§11).
- `checkpoints` and `checkpoint_repos` gain `beam`, keyed `(order_id, beam, seq)`. A checkpoint's `seq` is the beam's message seq, and a resumed order's second beam numbers from 1 again. The cargo bay directory becomes `<home>/cargo/<order>/<beam>-<seq>/`. New `store.LatestCheckpoint(order)` picks by insertion order (`rowid`); `ListCheckpoints` keeps ordering by `seq` and can't tell beams apart.
- `beams` gains `tour_no`, the tour that created the beam (§5).
- `orders` gains `parked_at TIMESTAMP`, set while the order's mission is parked (§7).
- `orders.priority` gets named levels: `store.PriorityRoutine, PriorityYellow, PriorityRed = 0, 1, 2`.
- New table `settings (key TEXT PRIMARY KEY, value TEXT NOT NULL)`, holding only `standing_orders` for now. `Store` gains `GetSetting` and `SetSetting(ctx, key, value, entry LogEntry)`, the latter logging in the same transaction like every other write.
- `crew.harness` defaults to `''`, and `store.InsertCrew` stops filling in `"sdk"`. An empty harness means "unset" and lets the division default apply (§2).

### 2. Roster config, divisions and standing orders

New `internal/bridge/roster.go`:

```go
type RosterConfig struct {
    Divisions      map[string]DivisionConfig `yaml:"divisions"`
    StandingOrders bool                      `yaml:"standing_orders"`
    Transporter    TransporterLimits         `yaml:"transporter"`
}
type DivisionConfig struct {
    Harness string `yaml:"harness"`
    Model   string `yaml:"model"`
}
type TransporterLimits struct {
    MaxBeams        int `yaml:"max_beams"`        // default 18
    MaxProvisioning int `yaml:"max_provisioning"` // default 3
    RatePerMinute   int `yaml:"rate_per_minute"`  // default 5
}
func LoadRoster(path string) (RosterConfig, error) // strict YAML (KnownFields), as cmd/bmus/order.go decodes orders; a missing file is a zero config
func CheckRoster(r *RosterConfig) error            // division names are identifiers; zero limits take the defaults
```

`Config` gains `Divisions`, `StandingOrders` and `TransporterLimits` (the name `Transporter` is taken by the provider). `bmus bridge run` gains `--roster <path>`, default `<home>/roster.yaml`, loaded next to `parseRepoFlags`.

The roster's `standing_orders` is only a default. `Daemon.StandingOrders` seeds the `settings` row from it on first read, and from then on the live toggle wins. `Daemon.SetStandingOrders(ctx, on)` writes the row, logs `standing orders on/off` and, when turning them on, wakes every division (§4). CLI: `bmus standing-orders [on|off]`, printing the current value with no argument. RPC: `standing_orders.get`, `standing_orders.set`.

Division defaults (#59) resolve in two places. `provision` passes `resolveHarness(crew)`: the crew member's harness, else the division's, else `""` (serve's default, sdk). `orderModel` becomes `resolveModel(order, crew)`: the order's, else the crew member's, else the division's, else `""`. Both return the source with the value. `CrewView` gains `harness_source` and `model_source` (`crew`, `division`, `default`), which #59's "`crew list` shows the source of each value" needs. `AddCrew`, `CreateOrder` and `RouteOrder` reject a division missing from the roster, and `AddCrew` checks the resolved harness against `Config.Harnesses`.

### 3. Priority, withdraw and route

`cmd/bmus/order.go`'s order file gains `priority: routine|yellow|red` (default routine; anything else is a parse error). Its "assignee is required" check becomes "assignee or division is required". `CreateOrder` already handles an empty assignee, and `InsertOrder` makes it a pool order.

`store.WithdrawOrder` moves an order to `withdrawn` only from `pool` or `directed`, in `SettleOrder`'s conditional-write style. `Daemon.WithdrawOrder(ctx, id, reason)` turns any other state into a bad request naming it ("order ORD-0007 is done, too late to withdraw"). An unclaimed order has no mission to tell. A recalled order still has its parked mission, and withdraw rejects it ("parked; use belay").

`store.RouteOrder` sets assignee, division and state (directed with an assignee, else pool), again only from `pool` or `directed`. `Daemon.RouteOrder(ctx, id, assignee, division *string)` validates a new assignee as `CreateOrder` does, then signals the assignee's tour with `order_assigned` or, for a pool order, wakes the division.

CLI: `bmus order withdraw <id> [--reason]`, `bmus order route <id> [--assignee <crew>] [--division <division>]`. RPC: `order.withdraw`, `order.route`.

### 4. Standing-orders dispatcher

Spec §5: "for each on-deck crew member, take the oldest highest-priority *directed* order first; if standing orders are on, take the highest-priority *pool* order whose division matches."

- `store.ClaimOldestDirectedOrder` orders both its queries by `priority DESC, rowid ASC`.
- New `store.ClaimOldestPoolOrder(ctx, crewID, division, entry)` claims `state = 'pool' AND division = ?` in the same order and sets `assignee = crewID`, `state = 'away'`. An empty division matches nothing. A claimed pool order is then indistinguishable from a claimed directed one.
- `claimOrder` tries the directed claim, then, when `StandingOrders` reads true, the pool claim for the crew member's division. Both report whether the order's mission is parked (§8).

I'd rather reuse the tour's `order_assigned` signal than add the singleton Dispatch workflow from spec §5. `Daemon.wakeDivision(ctx, division)` sends `order_assigned` to the tour of every on-deck crew member in the division, outside any workflow and best effort, logging a failed send as `CreateOrder` does today. The claim's `UPDATE ... RETURNING` is the only lock, and tours that lose the race find nothing. A crew member coming on deck claims before its first wait, and an idle tour that missed a signal re-checks after `crewTourWaitTimeout`. Red-alert preemption of an order already away stays out of scope (spec §11, open question 4).

### 5. Transporter queue and beam cap

Provisioning moves into a child workflow, `transporterWorkflow` (registered name `"transporter"`, ID `beam/<crew>/<tour>` as in spec §5), which the tour runs on a DBOS queue and waits on, both recorded in the tour:

```go
q, err := dbos.RegisterQueue(dbosCtx, "transporter",
    dbos.WithGlobalConcurrency(limits.MaxProvisioning),
    dbos.WithRateLimiter(&dbos.RateLimiter{Limit: limits.RatePerMinute, Period: time.Minute}))
```

All of these, and `WithQueue`, exist in the pinned DBOS Go v1.7.0. The workflow has two steps:

1. `remove-previous`: if the crew member's latest `beams` row belongs to an earlier tour and the beam still exists, remove it. A failure is logged and left to the beam's TTL.
2. `provision`: today's logic, except that it reuses the latest `beams` row only when the row has this tour's `tour_no`, and refuses a dismissed crew member (the tour then ends dismissed). A crash retry still reuses its beam, and a new tour never picks up its predecessor's sick or expiring beam.

The queue paces beam creation. The 20-beam tenant cap needs its own check. Each crew member holds at most one beam: a tour removes its predecessor's beam before creating one, and dismissal removes the beam too (§8). `AddCrew` rejects a new crew member once the non-dismissed crew reaches `MaxBeams` (default 18, D8's "roster ≤ ~18"), and the two spare slots absorb beams whose removal failed until their TTL.

Watch change therefore breaks before it makes, and a crew member spends a few minutes a day without a beam. I think that is cheaper than a second beam per crew member against a 20-beam cap.

### 6. Combadge: stand_down, recall and handover

Of the bridge-to-beam types `checkpoint`, `stand_down`, `recall` and `belay`, Phase 2 sends the last three. `checkpoint` stays unsent and unhandled.

- `stand_down` and `recall` mean the same thing to a harness: reach a safe point, write a checkpoint and stop. Holodeck and echo write their placeholder checkpoint at once. The sdk harness switches `query()` to a streaming-input prompt, closed after the first result, and on either command pushes a user message asking the agent to call `request_handover`. If no checkpoint lands within 10 minutes, the harness writes one itself with a stub note naming the order. When the session has no transcript, it writes an empty `transcript.jsonl` (`writeCheckpoint` throws today). The checkpoint that answers the command carries `stopping: true` (new `CheckpointReadyBody` field), and `run()` then rejects with a `Stopped` error.
- `serve.ts` treats `Stopped` as a third way for a run to end, next to report and error. It emits nothing and records the order neither running nor completed. A restarted serve then reports no `combadge_restarted`, and a later `order` command for the same id runs. Before that run, serve removes the order's repo checkouts, `out/` and checkpoint directories and keeps `in/`, where the bridge has just shipped the new bundles. A checkpoint that fails during a stand_down still ends in `error`.
- `belay` already works: the sdk and holodeck harnesses abort and reject, and serve emits an error.
- `OrderBody` gains `handover` (optional string, the note the order resumes from). Go and TS structs, `protocol/messages.schema.json` and the golden fixtures for `order` and `checkpoint_ready` change. The sdk prompt adds the handover next to the dossier and, when there is one, presents the checkout's starting commit as the checkpoint it resumes from.

`checkoutRepos` needs no change. A resumed bundle's tip becomes the checkout's `origin/bmus/<order>`, the commit later thin bundles exclude.

### 7. Mission lifecycle: park and resume

A mission can now outlive its beam and its crew member. It parks when its beam goes away (watch change, beam loss) and when the captain recalls its order, and it resumes on whichever crew member claims the order next. The mission ID stays `order/<id>`, and one mission carries an order from claim to its terminal state. Missions register with `WithMaxRecoveryAttempts(-1)`, as tours do: a parked mission may live through many restarts.

The mission's state lives in local variables set only from recorded `Recv` results: `crewID` (starts as `in.CrewID`), `tourID` (for `ship-repos`), `parking`, `recalling`, `parked`. Every use of `in.CrewID` in the mission becomes `crewID`, and `runMission` returns `crewID` with its result for `missionWorkflow`'s `bridge_error` path. `mission_done` and the new `mission_parked` go to the current tour of the crew member the mission ran on, read by a `current-tour` step. A send to a tour that doesn't exist yet (a crash between `NextTour` and the tour's start) counts as delivered: that tour finds the order's state when it claims.

`store.ParkOrder` sets `parked_at` and logs `order parked: <reason>` only while it is empty, and a re-run writes nothing. The `unpark` step clears it on `resume`, and `SettleOrder` clears it on every terminal state.

The bridge drives the mission with synthetic messages on `fromCrewTopic`, the pattern `AnswerHail` and `endTour` already use:

| Message | Sent by | Running mission | Parked mission |
|---|---|---|---|
| `stand_down` | tour, at watch change | a step sends the real `stand_down`; `parking = true` | dropped |
| `recall` | `RecallOrder` | a step sends the real `recall`; `recalling = true` | `recall-order` with a non-empty `crewID`, else dropped |
| `belay` | `BelayOrder` | `order-belayed` closes an open hail and settles `belayed`; a step sends the real `belay`; returns `MissionBelayed` | `order-belayed`; returns |
| `error`, code `beam_lost` | tour, on heartbeat_missed | `park` on the existing checkpoints (it used to fail the order) | dropped |
| `error`, code `dismissed` | tour or `DismissCrew` | fails the order, as today | fails the order |
| `resume` | the claiming tour | dropped | `unpark`; `crewID`, `tourID` from the body; re-ship and send the order with its handover |

`resume` never goes on the wire. It is a `comms.Message` literal with body `{crew_id, tour_id}` (`comms.NewMessage` only knows wire types). Beam messages and the tour's synthetic `stand_down`, `beam_lost` and `dismissed` name a crew member (`Message.Crew`; the pump already drops a beam message naming another), and the mission drops one that doesn't name `crewID`. A late message from a beam the order has left, or a dismissal of a crew member it no longer has, then never reaches the order's current run. `resume`, `belay` and `recall` target the order itself and skip the filter. A parked mission drops every other message with a log line, and its `Recv` loops on timeout with no deadline of its own: the order sits either in the pool or with a crew member in sickbay, both visible to the captain.

Changes to the existing handling:

- `checkpoint_ready` is pulled as today. Only one with `stopping` then acts: with `recalling` it runs `recall-order`, with `parking` it runs `park`. A voluntary checkpoint that lands while the stop is pending is just a checkpoint.
- An `error` while parking or recalling (the harness couldn't checkpoint) parks or recalls on the existing checkpoints.
- A `report` that beats the stand_down or recall completes the order.
- A failed `stand_down` or `recall` send parks or recalls on the existing checkpoints. A failed `belay` send still settles the order. After a failed `recall` or `belay` send the beam may still be running the order, and `mission_parked` or `mission_done` carries `StaleBeam`. The tour then ends in sickbay, as on beam loss, and the captain re-energizes a fresh beam.

`park` closes an open hail ("closed unanswered: mission parked") and calls `ParkOrder`. If the tour's backstop already failed the order, the mission returns `MissionFailed`. `recall-order` closes an open hail and runs `store.RecallOrder`: from `away`/`hailing` and only while `assignee` is `crewID`, it moves the order to `pool`, clears `assignee`, sets `parked_at` and logs, in one transaction. A re-run finds the order moved and writes nothing. The step then calls `wakeDivision` on the order's division. Either way the mission sends `mission_parked` and parks; after a recall it sends to the recalled crew member's tour first and then empties `crewID` until a `resume`. `order-belayed` settles a parked order from `pool` as well as `away` and `hailing`.

`ship-repos` ships from `LatestCheckpoint` when there is one. Under one `lockRepo`, it checks and fetches the checkpoint's cargo bundle into the bridge's clone as `bmus/<order>` (the `fetchBundle` logic, §10, called without taking the lock again) and bundles that branch with full history. A bundle the check rejects is logged `work_rejected`, and the step falls back to the previous checkpoint and finally to `base_ref`. Its retry predicate skips `errWorkPermanent` as well as `errRepoPermanent`. With no checkpoint it ships from `base_ref` as today. `send-order` fills `handover` from the same checkpoint's note.

### 8. Watch change, re-energize and dismissal

**Deciding when.** The tour computes `watchAt = beam.ExpiresAt - lead` from the recorded transporter result, with `lead` one hour (D5) and `Config.watchChangeLead` for tests. Every `Recv` in the main loop caps its timeout at `time.Until(watchAt)`, with a floor of one millisecond. After a timeout a `watch-due` step records whether `watchAt` has passed, and the tour branches only on that result. This is `endTour`'s rule: whether to act comes from recorded outcomes, never from the clock during replay.

**Handing over.** When watch change is due:

1. If a mission runs, the tour sends it `stand_down` and waits for `mission_parked` or `mission_done`, keeping the pump up for the beam's `checkpoint_ready`. The wait has a recorded deadline of 30 minutes. Past it, the tour sends `beam_lost` ("watch change: no checkpoint in 30m") and waits `missionSettleTimeout` more, then backstops a mission that still hasn't parked. During the wait, heartbeat_missed for the tour's beam sends `beam_lost` at once and the tour ends in sickbay; `dismissed` sends the dismissal error and the tour ends dismissed; `crew_error` is logged as in the main loop. Other signals are dropped, as in `endTour` today.
2. `markTourEnded`, `StopPump`.
3. Step `next-tour`: `store.NextTour(crewID, from)` sets `tour_no = from+1` and clears `current_beam`, only while `tour_no` is `from`, and logs the rotation. A re-run writes nothing. With `current_beam` empty, `ensurePumps` on a restart can't attach the new tour's pump to the old beam.
4. The tour starts the next tour from its workflow body, with the deterministic ID `tourWorkflowID(crew, from+1)`. A replay gets the existing handle. If the process dies between steps 3 and 4, the replay reaches step 4, and `attachCrewTours` also starts `crew.tour_no`'s tour at launch.
5. The tour ends as `watch_change`. The next tour's `remove-previous` removes the old beam.

`endTour` takes the synthetic message as a parameter and accepts `mission_parked` in its settle wait, and `tour-end` skips the backstop when the mission parked. A recall and another crew member's claim can move the order between a settle wait's timeout and the backstop. `backstop` therefore settles only while the order's assignee is the tour's crew member and closes only that crew member's hails, in `tour-end` and `settle-mission` alike. Dismissal and beam loss keep calling `StopPump` before the wait (their beam is going or gone). In the main loop, `mission_parked` for the running order (a recall) sets the crew member back on deck without a backstop and clears `running`: the mission is alive and no longer this tour's.

**Resuming.** `claimOrder` reports `Parked` when the order it returns has `parked_at` set: a directed order already away (watch change, re-energize) or a recalled pool order. The already-away branch also sets the crew member away (conditionally, logged only on change). The tour gets the parked mission's handle from its ID and sends it `resume` with its crew member and tour ID; its pump is up by then. `unpark` acts only while the order is `away` with the body's crew member as assignee. A recall or belay that reaches the parked mission first leaves it nothing to do, the mission drops the `resume`, and the tour learns the outcome from `mission_parked`, `mission_done` or `mission-alive`.

This changes Phase 1's beam-loss behaviour: the mission parks, the crew member goes to sickbay as before, and the order stays `away` until re-energize, a recall, a belay or dismissal. Three tests change:

- `TestSickbayMidMission` (`internal/bridge`): order `away`, mission pending, an `order parked` entry and no `fail` entry, in place of `failed`, `MissionFailed`/`beam_lost` and the `fail` entry.
- `TestCrewSickbayOnBeamLoss` (`cmd/bmus`): `bmus order list` shows the order `away`, and the log has `order parked` and no `beam_lost` failure.
- `TestShipReposAfterTourEnded` (`internal/bridge`): the synthetic `beam_lost` parks the mission (still pending, no settled order) instead of returning `MissionFailed`.

**Re-energize.** `Daemon.ReenergizeCrew(ctx, crewID)` requires sickbay. If tour `crew.tour_no`'s workflow is pending or enqueued, it returns nil, re-energize being under way. If that workflow doesn't exist (a crash after the bump), it starts it. Otherwise it calls `store.NextTour` and starts tour `tour_no+1` under the same deterministic ID. Repeated calls start one tour. Re-energize stays manual: the mock has it as a captain's button, and an automatic retry would hide a beam that keeps failing. CLI: `bmus crew reenergize <id>`. RPC: `crew.reenergize`.

**Dismissal.** Dismissal is what frees a beam slot. `Daemon.DismissCrew(ctx, id)` looks at tour `crew.tour_no`'s workflow. A pending or enqueued tour gets the `dismissed` signal, and its `tour-end` sets the crew member dismissed, followed by a best-effort `remove-beam` step. Otherwise (the tour ended in sickbay, or hasn't started yet), one transaction sets the crew member dismissed and sends the `dismissed` error to the mission of a parked order still assigned to it, and the beam is then removed best effort. A tour started later finds the crew member dismissed in `provision` and ends. CLI: `bmus crew dismiss <id>`. RPC: `crew.dismiss`.

### 9. Recall and belay

`Daemon.BelayOrder(ctx, id, reason)` and `Daemon.RecallOrder(ctx, id, reason)` log the request and send the synthetic message to the order's mission in one store transaction (`dbos.WithSendTransaction`, as in `AnswerHail`). Belay takes an order that is `away`, `hailing`, or in the pool with `parked_at` set (a recalled order). Recall takes `away` or `hailing`. A parked order qualifies only while its crew member is in sickbay, the case recall mostly exists for; one being handed to a new beam is rejected ("being resumed by <crew>; try again").

The mission reads both in order and stays alive after a recall, and a belay that follows a recall is never lost. A second recall the mission reads while recalling is logged and dropped. The beam commands go out from mission steps, the only place `SendCommand` is safe.

Recall needs a division. A directed order without one has no pool to return to, and recall rejects it with a pointer to `order route` or `order belay`. Any crew member of the division may claim the recalled order next, the recalled one included. I'd keep it that simple, with no column remembering who was recalled: the captain routes the order to pin it elsewhere.

CLI: `bmus order belay <id> [--reason]`, `bmus order recall <id> [--reason]`. RPC: `order.belay`, `order.recall`.

### 10. Bundle checks and bridge-side push (#65)

#65 lands first. Both checks apply to every bundle the bridge fetches (report work and the checkpoints `ship-repos` lands).

- Objects: `fetchBundle` strips the bundle's header and pipes the pack through `git index-pack --strict --fix-thin --stdin` in a throwaway bare repository that borrows the clone's objects through `objects/info/alternates`. It fetches into the clone only after that passes. The check works on git 2.43, which skips `transfer.fsckObjects` for bundles. A failure is `errWorkPermanent`: a `work_rejected` log entry, no branch change, the bundle left in the cargo bay.
- Size: the transporter gains `Size(ctx, beam, path) (int64, error)` (`stat -c %s` over `Exec` on tsh, `os.Stat` on holodeck). `pull-work` and `pull-checkpoint` check every bundle against `Config.MaxBundleBytes` (default 2 GiB) before copying, and fail with `bundle_too_large`.

Push stays a CLI action. The mock has no push button, and I'd rather keep the one write to a shared remote behind an explicit command. `Daemon.PushOrder(ctx, id, target string, force bool)` requires the order to be `done`. Under each repo's `lockRepo` it checks that `bmus/<order>` in the bridge's clone is at the commit the done entry's payload recorded for that repo, refuses otherwise (a repo with a `FetchError` never matches), and runs `git push origin bmus/<order>:<target>`, with `-f` only on `--force`. `origin` is the registered URL, and `target` defaults to `bmus/<order>`. CLI: `bmus order push <id> [--target-branch <name>] [--force]`. RPC: `order.push`.

### 11. Inbox dedup and the crew-status guard (#22, #48)

#22: the inbox key gains `tour_no`, the issue's second option. It needs no combadge change, and each pump already belongs to one tour. `SeenInbox`, `InsertInboxSeq`, `RecordInbox` and `ContiguousInboxSeq` take `tourNo`, and `comms.PumpConfig` gains `TourNo`, set by `EnsurePump`.

#48: one race remains. A mission stuck past its tour's settle wait is backstopped, and the next tour claims another order. A late `record-hail` from the old mission would then set the crew member `hailing` for the wrong order. The crew-status updates in `InsertHail` and `decideOpenHail` gain `AND EXISTS (SELECT 1 FROM orders WHERE id = <the hail's order> AND assignee = crew.id AND state IN ('away', 'hailing'))`, with no new column. The issue body's `setMissionCrewStatus` no longer exists and gets corrected to these two methods.

### 12. Red alert in the status condition

`ReadStatus` also reads the ids of open red orders (`pool`, `directed`, `away` or `hailing` with `PriorityRed`) into `StatusSnapshot.RedOrders`. `statusOf` turns red when there are any, with reasons `<order-id> red alert` in id order after the sickbay reasons. This closes the open item in `spec/phase-1-plan-amendment-2026-10-18.md`.

### 13. Console (#71-#78)

`spec/console-plan-2026-10-18.md` stands as written for #71-#77. #78 wires its action table's Phase 2 rows to `BelayOrder`, `RecallOrder`, `WithdrawOrder`, `RouteOrder`, `ReenergizeCrew` and `SetStandingOrders`, each a thin handler behind #71's session, Origin and CSRF checks and each matching a CLI command above. Push stays off the console.

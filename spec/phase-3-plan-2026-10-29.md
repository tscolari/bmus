# BMUS Phase 3: Chain of command

## Context

`spec/initial-plan-2026-10-16.md` §9 scopes Phase 3 as: Command's consult lane; the Regulations engine and `regs.yaml`; routing, re-check and the countermand window; Command splitting orders into child orders; hail parking for long waits; metrics for the auto-resolved share, captain overrides and time-to-answer. Exit: a table-driven test suite proves no captain-only category is ever auto-answered, including Command picking a captain-only option, and a week of use reports the measured escalation and override rates.

Every Phase 2 issue has landed (`spec/phase-2-plan-2026-10-19.md`); its epic, #55, waits only on its real-beam acceptance run. The Phase 3 epic is #56, with one sub-issue filed so far, #54 (the optional tracker interface, needed for Command's mission lane to split an RFC into tickets). Nothing else is filed; this plan schedules the rest.

Three things already exist, laid down ahead of time by earlier phases:

- The `hails` table carries `category`, `route`, `decided_by`, `rationale`, `confidence` and `countermand_until` (`internal/store/schema.sql`), all unused past Phase 1's `route='captain'` default and `decided_by='captain'`.
- `internal/comms/protocol.go` already defines `TypeConsult`/`TypeConsultReply`, `ConsultBody`/`ConsultReplyBody` and `DecidedByPolicy`/`DecidedByCommand`/`DecidedByCaptain`, each marked "Command lane only; unused in Phase 1."
- `orders.parent_id` exists on every order, unused since Phase 1 (§7: "lets Command split a big order into children; the parent waits on its children and closes when they do").

This plan wires those three up rather than inventing new shapes for them. It also settles two of the open questions in §11.

Command runs in its own beam as a crew member of a new, reserved division, `command`. That closes "is Command's placement in a beam the right default" for v1: yes, and the interface stays portable as intended.

With more than one crew member in that division, the first one on deck by id answers consults. This is a provisional tie-break, not a real "first officer" concept, and it narrows the open question without closing it.

Red-alert preemption (open question 4) stays out of scope; the epic's acceptance criteria don't ask for it.

## Approach

### 1. Schema

New columns go into `schema.sql` and into `addedColumns`, the way #58, #100 and #141 added theirs, and an existing bridge database opens unchanged. `workflowVersion` stays `"1"`.

- `hails` gains `created_at TIMESTAMP`, `decided_at TIMESTAMP`, `countermanded_at TIMESTAMP` and `original_decided_by TEXT NOT NULL DEFAULT ''`. `created_at` is nullable because `ALTER TABLE` can't add a `NOT NULL` column without a constant default; hails from before this change keep it NULL, and metrics (§9) skip them. `decided_by` keeps meaning "who the decision stands as now" (it flips to `captain` on a countermand); `original_decided_by` is set once, at the first decision, and never changes: a countermand doesn't erase that the hail was first auto-answered or decided by Command. `InsertHail` sets `created_at`; `decideOpenHail` sets `decided_at` (the entry's timestamp, UTC, like every other timestamp column) and, only while `original_decided_by` is still empty, sets it to `decided_by`.
- A new `settings` key, `command_guidance`: free text the captain sets for Command's consults (§5). It reuses the `settings` table Phase 2 already added, no schema change beyond the key itself. `bmus command guidance set/show` (RPC `command.guidance.set`/`.get`) edits it.
- `orders` gains one state, `split` (§8). No new columns: `orders.parent_id` and `orders.division` already carry everything order splitting needs. No changes to `crew` or `beams`.

### 2. Regulations engine (`internal/regs`) and `regs.yaml`

A new package, matching the name `spec/initial-plan-2026-10-16.md` §12 already proposed for it. It owns the match rules alone: no store access, no DBOS, plain functions over a `regs.Hail` the caller builds from `store.Hail` plus the order's division and priority.

```go
type Config struct {
    Classify         []ClassifyRule `yaml:"classify"`
    CaptainOnly      []MatchRule    `yaml:"captain_only"`
    AutoAllow        []MatchRule    `yaml:"auto_allow"`
    CommandMayAnswer struct {
        MinConfidence     float64       `yaml:"min_confidence"`
        CountermandWindow time.Duration `yaml:"countermand_window"`
    } `yaml:"command_may_answer"`
    Escalation struct {
        CaptainReminderEvery time.Duration `yaml:"captain_reminder_every"`
        OnTimeout            string        `yaml:"on_timeout"` // hold | belay | default_option
        CaptainTimeout       time.Duration `yaml:"captain_timeout"`
        DefaultOption        *int          `yaml:"default_option"`
    } `yaml:"escalation"`
}
type ClassifyRule struct{ Tag, Tool, Match string }
type MatchRule struct{ Category, Tag, Tool, Match, Option, Alert string }
```

`LoadRegs(path string) (Config, bool, error)` decodes strictly, like `LoadRoster`; a missing file returns a zero `Config` and `found=false`. `CheckRegs` compiles every `Match` regex once at load, so a bad one fails startup rather than the first matching hail. `bmus bridge run --regs <path>`, default `<home>/regs.yaml`.

`Daemon.regsConfigured` is that `found` bool. While it's false, the hail workflow's classify step (§3) never calls `Classify` at all: every hail routes straight to the captain, logged "regs.yaml not configured." That's a deliberate exception to `Classify`'s own default below: an unconfigured bridge has no `captain_only` list to protect anything Command might otherwise rubber-stamp. `bmus status` lists it as information, never as a yellow reason. Once a `regs.yaml` exists, even a nearly empty one, `Classify` checks `captain_only` first, then `auto_allow`, and defaults anything neither matches to `RouteCommand`, matching the hail flow diagram in `spec/initial-plan-2026-10-16.md` §5 (`auto_allow` / `command_first` / `captain_only`). Checking `captain_only` first, unconditionally, is what makes the exit criterion provable: no `auto_allow` rule and no command-routed default can apply to a hail a `captain_only` rule also matches.

The illustrative `regs.yaml` in the initial plan writes `captain_only` and `auto_allow` entries against categories (`destructive`, `scope_change`, `egress`, `access_request`, `external_effect`) that no hail carries today; a `tool_approval` hail's `category` is always `tool_approval`, with the tool and its command sitting in `context`. `classify` closes that gap: each rule names a `Tag` and, for a `tool_approval` hail, a `Tool` and a `Match` regex tested against `context.input`'s command (Bash) or a tool-specific field. The first match wins and sets the hail's tag, empty when none match (routine). `captain_only` and `auto_allow` rules then match on either `Category` (today: `clarifying_question`, `tool_approval`, and `order_split`, §8) or the classified `Tag`, plus an `Alert` level (`red`) when given, checked against the order's own priority. A `captain_only` rule may instead set `Option`, a regex over the option label Command picks or the free-text answer it gives; only `CheckAnswer` reads those (below).

Classification collapses runs of whitespace in the command before any regex runs. `auto_allow` fails closed:

- Its `Match` regexes match the whole command, as if anchored with `^...$`.
- A command containing `;`, `&&`, `||`, `|`, `` ` ``, `$(` or a newline is never auto-allowed, whatever the rules say. `go test ./... && git push` goes to Command or the captain like any unmatched hail.

Shell parsing isn't attempted: refusing those characters can only err toward asking. `captain_only` tag regexes stay substring matches, where over-matching only costs the captain a hail.

A shipped default lives in `internal/regs/default.yaml`, embedded. `bmus regs init` writes it to `<home>/regs.yaml` with a header saying it's a starting point. The bridge never writes it on its own: switching on auto-allow and Command routing changes who decides, and that takes an explicit act. Until then every hail goes to the captain. The default:

- tags `git push`, `git push --delete` and the like as `external_effect`, and `rm -rf` and `DROP TABLE` as `destructive`, and lists both under `captain_only`;
- tags `bash -c`, `sh -c` and `eval` as `external_effect`;
- adds a `captain_only` `Option` rule, `(?i)delete|destroy|force`;
- auto-allows `go test ./...`, `go build ./...`, `npm ci`, `npm install` and `make lint` on `Bash`, mirroring the initial plan's own example.

These defaults are a starting point, not a considered security policy; the captain is expected to tighten or loosen them once real hails start arriving.

Two functions do the work the hail workflow needs:

- `Classify(h Hail) (route, tag, rule string)` returns one of `RouteAuto`, `RouteCaptain` or `RouteCommand`, the tag it matched (for the log) and which rule fired (for the auto-allow decision's rationale).
- `CheckAnswer(h Hail, reply ConsultReply) (ok bool, reason string)` re-applies `captain_only` to Command's proposed answer. It tests the picked option's label, or the free-text answer, against every `captain_only` rule with `Option` set. A hail that is itself routine, but whose proposed answer picks a captain-only option (an `AskUserQuestion` offering "destroy the branch" among its choices, say), still escalates. It also rejects `reply.Decision == "escalate"` outright, and any `reply.Confidence` below `CommandMayAnswer.MinConfidence`, regardless of whether a rule matches.

### 3. Hail workflow: classification, routing and the consult round trip

A new workflow, `hail/<id>`, registered as `"hail"` (`internal/bridge/hail.go`), fills the fourth row of `spec/initial-plan-2026-10-16.md` §5's workflow table, left unbuilt since Phase 1. The mission starts it, without waiting on it, the moment it records a hail:

```go
case comms.TypeHail:
    ...
    id, err := dbos.RunAsStep(ctx, func(c context.Context) (string, error) {
        return recordHail(c, daemonFrom(c), cur, body)
    }, ...)
    ...
    if _, err := dbos.RunWorkflow(ctx, hailWorkflow, HailInput{HailID: id},
        dbos.WithWorkflowID(hailWorkflowID(id))); err != nil {
        return MissionResult{}, cur.CrewID, err
    }
    hail = &openHail{ID: id, Ref: body.Ref}
```

This is the same idiom `crewTourWorkflow` already uses to start `missionWorkflow`: a child workflow started inline, under a deterministic id, never awaited by its parent. The hail workflow and the mission talk only through `fromCrewTopic`, both ways. The mission's own loop stays exactly as it is today: a captain's, Command's or a policy decision all arrive as the same synthetic `comms.TypeAnswer` message it already handles in `case comms.TypeAnswer`. That branch currently overwrites `body.DecidedBy = comms.DecidedByCaptain` unconditionally; this plan removes that line. The sender, now three possible senders rather than one, sets it correctly, and the mission just relays what it is given to the beam.

The workflow:

1. Step `classify`: read the hail and its order (for division and priority). While `d.regsConfigured` is false, route `captain` at once, logged "regs.yaml not configured." Otherwise call `regs.Classify`. On `RouteAuto`, decide at once: step `decide-policy` runs the same transaction shape as `AnswerHail` (`DecideOpenHail` with `decided_by=policy`, the matched rule's text as rationale, sending the synthetic answer to the mission under `dbos.WithSendTransaction`). The workflow ends; the hail never shows as open in the console beyond the instant it existed, and `bmus hails list` still shows it decided with `decided_by policy`, for the audit trail.
2. On `RouteCaptain`, or when the hailing crew member is itself in the `command` division (D7: "Hails from Command go to the captain"), step `route-captain` sets `hails.route = "captain"` and logs why ("captain-only: <tag>", or "from Command"), then moves to step 6.
3. On `RouteCommand`, step `find-command` looks up the single on-deck crew member of the `command` division (`Daemon.commandCrew`, first one on deck by id). None found, whether because no crew member is in that division or the one that is isn't on deck, falls back to step 2's captain route, logging "Command not on deck" instead. `StatusSnapshot` gains `CommandDown bool`, read alongside the open-hail check `ReadStatus` already does: true when `regs.yaml` is configured, at least one crew member is in the `command` division, and none of them is on deck. `bmus status` shows it as a yellow reason. A bridge with nobody in that division never raises it: a permanent yellow would teach the captain to ignore yellow.
4. Step `transmit-consult` builds a `comms.ConsultBody` (the hail's own fields, the order's title and body as `OrderSpec`, the order's last 20 captain's-log lines as `RecentLog`, the `command_guidance` setting as `Guidance`, and the matched tag or rule as `Regulations`, a short excerpt rather than the whole file) and sends it to Command's crew member with `SendCommand`. Then `dbos.Recv[comms.Message](ctx, "consult-reply", consultTimeout)`, default 10 minutes and configurable. A timeout falls back to step 2 the same way, logged "Command did not reply within <t>." Command going to sickbay mid-wait isn't separately wired: a dead beam answers nothing, and the same timeout covers it.
5. The reply decodes to `comms.ConsultReplyBody`. `regs.CheckAnswer` runs against it. A rejection, whether `escalate`, below `min_confidence`, or a captain-only proposed answer, falls back to step 2, logged "Command escalated: ..." or "Regulations rejected Command's answer: ...". Otherwise step `decide-command` resolves the answer's text (the picked option's label, or `reply.Answer`), writes `hails.confidence` and `hails.countermand_until = now + CountermandWindow`, decides with `decided_by=command`, and sends the synthetic answer. The workflow ends.
6. The captain path (steps 2 or 3's fallback) stays open longer: it waits for the existing `AnswerHail` RPC to decide the hail, exactly as it always has, with two additions while it waits. A reminder loop logs ("hail H-0091 still open, N minutes") every `captain_reminder_every`. Past `captain_timeout` (0 disables it), `on_timeout` applies once: `hold` does nothing, leaving the mission's own, much longer, `missionWaitTimeout` as the real backstop, unchanged from Phase 1; `belay` calls `BelayOrder` on the hail's order; `default_option` answers with `escalation.default_option` through the same policy-decide path step 1 uses, logging that the timeout decided it, not a rule, and sets `countermand_until` (§6). `default_option` never applies to a hail a `captain_only` rule routed here: those fall back to `hold`, which keeps the agent waiting. "Only the captain decides this" has no exception for a slow captain. The workflow ends once `AnswerHail` or the timeout policy decides the hail; it never itself calls `DecideOpenHail` for a captain's answer, which stays `AnswerHail`'s job exactly as today.

`hailWorkflowID(id string) string { return "hail/" + id }`. The workflow's result is `{Decided bool, By string}`, read by nothing today, kept for a later metrics pass that might read DBOS's own workflow history instead of (or alongside) the log.

### 4. Routing consult replies: pump and Sink

`consult` and `consult_reply` carry no `Order` (the protocol doc comment already says so). `internal/comms/pump.go`'s `dispatch` can't route them the way it routes hail, checkpoint and report messages, by `missionWorkflowID(msg.Order)`. It gains one more case:

```go
case TypeConsultReply:
    var b ConsultReplyBody
    if err := json.Unmarshal(msg.Body, &b); err != nil || b.HailID == "" {
        p.log.Warn("comms: dropping consult_reply with a bad body", "seq", msg.Seq, "err", err)
        return nil
    }
    return p.cfg.Sink.ToHail(ctx, tx.SQL(), msg, b.HailID)
```

`Sink` gains `ToHail(ctx context.Context, tx *sql.Tx, msg Message, hailID string) error`, implemented in `internal/bridge/pumps.go`'s `pumpSink` exactly like `ToMission`, but sending to `hailWorkflowID(hailID)` on topic `"consult-reply"` instead of to a mission on `fromCrewTopic`. A reply naming a hail workflow that doesn't exist, one the mission never started, or one long finished, returns `ErrUndeliverable`, the same as a stale message to a missing mission does today; the pump logs it as undeliverable after `UndeliverableAfter` rather than stalling Command's whole stream on it.

### 5. Command's consult lane (combadge)

Today `serve.ts`'s `handleCommand` only knows `order` and the `RELAYED` set (`answer`, `checkpoint`, `stand_down`, `recall`, `belay`); `consult` falls through to "ignoring unsupported command." It needs its own lane, independent of whichever order, if any, is running in `run`: Command's mission lane and consult lane work at once (D7). A consult arriving mid-order can't wait for that order to finish, and the order running can't pause for a consult either.

`handleCommand` gains a branch for `consult`, calling a new `handleConsult(msg)` that never touches `run`. `Harness` (`combadge/src/harness/types.ts`) gains an optional method:

```ts
consult?(req: ConsultBody, signal: AbortSignal): Promise<ConsultReplyBody>;
```

Only the sdk harness implements it; a harness that doesn't (`holodeck`, `echo`) answers `{decision: "escalate", rationale: "harness <name> does not run a consult lane", confidence: 0}` at once, from `serve.ts` itself, without calling into the harness. `serve.ts` emits the resulting `consult_reply` with no `order` field, same as the inbound `consult` had none.

The sdk harness's `consult` runs a single, fresh `query()`, independent of any session the order's `run` holds. It carries no tools at all (`allowedTools: []`): D7 says consults are read-only, and in any case Command's own beam's filesystem has nothing to do with the hailing crew member's repo or branch, which lives on a different beam. `ConsultBody` already carries every fact Command needs as text (`question`, `options`, `context`, `order_spec`, `recent_log`, `guidance`, `regulations`); a tool Command could call would only distract from that, or worse, hail back out of its own read-only lane. The system prompt demands one JSON object shaped like `ConsultReplyBody` and nothing else; a response that doesn't parse as one, or is missing `decision` or `confidence`, becomes `{decision: "escalate", rationale: "could not parse Command's reply", confidence: 0}`, which `regs.CheckAnswer` rejects on `decision == "escalate"` regardless of anything else. A consult that outruns its own short internal timeout (2 minutes, `SdkDeps.consultTimeoutMs`) aborts the same way and answers the same escalate reply; the bridge's own `consultTimeout` (§3) is the outer backstop for the round trip as a whole, network and queueing included.

### 6. Re-check, decision and the countermand window

§2 already covers classification's re-check of Command's answer. What's left is delivering a countermand once a hail is decided.

Two kinds of decision are countermandable: Command's (§3 step 5) and the timeout's `default_option` (§3 step 6). Both are judgements made without the captain, and both set `countermand_until`. An `auto_allow` decision isn't: it applies the captain's own written policy, and a wrong one is fixed in `regs.yaml`, not hail by hail. It sets no `countermand_until`, and the console offers no override on every `go test`. Neither is `AnswerHail`'s own answer: the captain already decided it.

`Daemon.CountermandHail(ctx, hailID, decision string, option *int, reason string) error` mirrors `AnswerHail`, but acts on a decided hail. It requires `status == HailDecided`, `original_decided_by` in `{policy, command}`, `countermand_until` set, and `now <= countermand_until`. `store.CountermandHail` is the matching store method, in `DecideOpenHail`'s transactional style: it sets `decided_by = "captain"`, `decision`, `rationale = reason`, `countermanded_at = now`, logs "hail H-0091 countermanded: <reason>" and runs a caller-supplied `fn(tx)`, failing with a new `store.ErrCountermandExpired` if the window has passed or the hail never had one.

What reaches the beam is not a second `answer`. The mission has already relayed the first one and cleared its in-memory `hail` pointer, and its existing `case comms.TypeAnswer` guard (`hail == nil || body.HailID != hail.ID`) would correctly drop a second one: nothing should pretend the agent's `canUseTool` callback can be re-resolved after the fact. A countermand instead sends a new bridge→beam message, `correction` (`CorrectionBody{HailID, Ref, Note}`; `protocol/messages.schema.json` and both golden fixtures gain it, the same way `handover` was added to `OrderBody` in Phase 2). `serve.ts`'s `RELAYED` set gains `correction`; delivery to a live session follows the exact mechanism `stand_down` and `recall` already use, a user message pushed onto the streaming input, worded as "The captain overrides the earlier answer to '<question>': <note>." If no order is running, the agent already finished and reported, or the countermand targets a `clarifying_question` the agent had nothing further to act on, `serve.ts` just logs and drops it, the same path `relay` already takes for any inbound command naming no live run. A countermand can redirect work still in progress; it cannot undo a tool call that already ran, and this plan doesn't pretend otherwise.

CLI: `bmus hails countermand <id> (--option <n> | --decision <text>) [--reason]`. RPC: `hails.countermand`. Both mirror `hails answer` down to the flag names; the only difference an operator sees is which hails accept it. `HailView` gains `confidence`, `countermand_until` and `original_decided_by`, so `bmus hails list` can show them without a new flag.

### 7. Hail parking for long waits (combadge)

D4: "Hail waiting has two modes. Short waits hold the agent's query open. Long waits ... park the mission: checkpoint, end the query, and resume the session later with the answer injected. v1 can ship with hold-only plus park-on-watch-change; general parking comes in Phase 3." This is entirely a sdk-harness concern. Nothing on the bridge changes, and the order stays `hailing` on the same beam throughout; the bridge can't tell a parked hail from a held one and doesn't need to.

Today `hail()` (`combadge/src/harness/sdk.ts:213`) is awaited inside `canUseTool` for as long as the answer takes, tied to the one `query()` the order's `run` holds open. Two hail categories go through `canUseTool`: `clarifying_question` (AskUserQuestion) and `tool_approval`. A new sdk harness flag, `--hail-park-after` (default 15 minutes, passed like `--claude-path`), sets how long either is held. Past it the harness parks the run: it aborts that `query()` and keeps the session id. An `order_split` hail is held inside the `split_order` tool's handler and never parks. A resumed Command could call `split_order` again and create a second set of children.

#145 ran this against the real SDK (`spike-hail-parking-2026-11-02.md`). The abort fires the held call's `signal`, and the held promise stays pending. Resolving it after the resume had no visible effect in the spike. `query({resume: sessionId})` keeps the session id and its context. The answer is the first message the harness sends. In the spike's run the agent then re-issued the same call under a new toolUseID. `canUseTool` approves that call without a second hail through an approval keyed on tool name plus input.

The spike's transcripts add two facts (the spike file's "What the transcripts show"). The aborted CLI takes one more model turn, and in two of three scenarios the model re-issued the call there. The CLI refused it itself and nothing ran, but the resumed session keeps a refusal the captain never gave. In one scenario the agent later repeated it in its handover note. On resume the CLI also sends its own "Continue from where you left off." ahead of the harness's message, and the transcript answers it with "No response requested." If "No response requested." is ever a real model turn, the model could act before it sees the answer. The harness creates the approval or deny entry before `query({resume})` starts.

Each message the harness sends on resume corrects the refusal:

- allow: "The captain allowed `<command>`. Any refusal of it earlier in this session came from the session being paused while it waited; the captain never refused it."
- deny: "The captain denied `<command>`: <decision>. Any refusal of it earlier in this session came from the session being paused while it waited; this is the captain's answer."
- `clarifying_question`: "The captain answered your question (<question>): <answer>. Any refusal of it earlier in this session came from the session being paused while it waited."
- stop: the stop request `stopRequest` builds today, then "Your request to run `<command>` was never answered. Any refusal of it earlier in this session came from the session being paused while it waited; the captain never refused it."

Today `hail()` races the answer against the stop's withdraw signal, the SDK's signal and the run's abort. Its `finally` deletes the `answers` entry as soon as any of them fires. A park keeps the entry. The harness marks the run parked before it aborts the query, and `hail()` then leaves its entry in place and records the ref with the hail's tool name and input. An answer arriving between the abort and the end of the first query is kept for the resume like a later one. The park aborts a per-query `AbortController` and leaves the run open; #154 has the detail.

Parallel tool calls can hold several hails at once (untested in #145). The park keeps every held ref, and the resume waits until all of them are answered, with every answer in the first turn the harness sends. A resume on the first answer would have the agent re-issue the calls still parked, each raising a second hail for a question the captain already has.

For Bash the approval's key is the whole input minus `description`, compared deep-equal. The model writes `description` as a UI label and may reword it on a re-issue. A different `timeout` or `run_in_background` hails again. Agent (Task) drops `description` the same way. Every other tool, MCP tools included, compares its whole input. The approval is single-use and expires when the resumed query ends or 10 minutes after it starts, whichever is first. A call that doesn't match hails as usual.

A deny records a single-use deny entry under the same key, with the same expiry. A matching re-issue is denied with the captain's text without a second hail, and a later one hails. A parked `clarifying_question` leaves no entry. The harness's message carries the answer itself (#145 didn't test this).

A `stand_down` or `recall` arriving while parked resumes the session with the stop request in place of the answers. In the spike's one run the agent didn't re-issue the parked call and wrote its handover. An agent that does re-issue it raises a hail, and `HailWithdrawn` denies it like any hail after a stop. A belay while parked has no query to abort, and the run rejects with "belayed: <reason>". A failed `query({resume})` rejects the run with its error. A hail that parks, then a watch change before the captain answers, gets its own test in §Verification.

The spike also tested an assumption combadge already makes. SDK 0.3.301 warns `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` ("canUseTool will not be invoked") on every query under bypassPermissions. On claude 2.1.258 a PreToolUse `ask` still reached `canUseTool`. Both canUseTool categories depend on that path. The CLI on a beam comes from the beam image, outside combadge's pin, and an upgrade that honours the warning would stop those hails with no test failing. #172 adds a self-check at serve startup: one minimal query whose hook asks for a harmless `true`. On a fail, serve queues a crew-level `error` with code `harness_check_failed` and the reason before it listens, sends no `hello`, and exits once the first attach has read it. The crew tour sends the crew member to sickbay with that reason. #172 also lists the alternative that removes the dependency.

### 8. Order splitting into child orders

Command's mission lane needs a way to turn one order into several, written back to the bridge rather than decided locally: only the bridge can write to `orders`. This reuses the hail and Regulations machinery rather than adding a second path: a new hail category, `comms.CategoryOrderSplit`, carried by a new in-process tool, `split_order({children: [{title, body, division, priority}]})`, exposed to the sdk harness only when it's running as Command. A new `--role command` serve flag, passed by the tour exactly when `crew.Division == DivisionCommand`, threads into `HarnessOptions.Role`; `ALLOWED_TOOLS` gains `split_order` only then. The tool's call becomes `HailBody{Category: "order_split", Context: {parent: order.id, children: [...]}}`, held the same way any other hail holds the agent, through the same `hail()` call.

The default `regs.yaml` lists `order_split` under `captain_only`: spawning new work needs the captain's say by default, and nothing here stops a captain who disagrees from loosening it later. Once decided (allowed), the mission's existing `case comms.TypeAnswer` branch runs one more step before sending the answer back: `create-children` calls `store.InsertOrder` once per child, `ParentID: in.OrderID`, division and priority from each child or the parent's own when a child omits them, and logs "order split into N children: ORD-0101, ORD-0102, ...". The answer carries the created ids as its decision text, and Command's own agent finishes its report normally.

The parent's mission ends with that report, like any other, and Command goes back on deck, free for the next order. Children can take hours, and Command's beam and mission lane stay free throughout.

When `create-children` ran for the order, the report's settle moves the parent to a new non-terminal state, `split`, instead of `done`. The console shows it as waiting on its open children. Status counts it with neither away nor open orders.

The store settles the parent. Every transaction that ends a child, whether done, failed, belayed or withdrawn, checks the child's siblings in the same transaction. When none is left open, it settles the parent too: done if every child ended done, failed otherwise, naming the failed children in the parent's entry. Recall puts a child back in the pool, still open, and doesn't count. The parent's state lives on the rows, and survives restarts, park and Command's own watch change.

Belaying the parent cascades (#146). Children still in the pool or directed are withdrawn, and children in flight are belayed through the normal belay path. The captain's belay was meant to stop that work, and the children are part of it. The CLI and console confirm text says how many children it affects.

### 9. Metrics

"Auto-resolved share," "captain overrides" and "time-to-answer" all read off the `hails` columns §1 added, nothing more:

```go
func (d *Daemon) HailMetrics(ctx context.Context, since time.Time) (HailMetrics, error)

type HailMetrics struct {
    Total, Decided, Countermanded       int
    ByOriginalDecider                   map[string]int // policy, command, captain
    MedianTimeToAnswer, P90TimeToAnswer time.Duration
}
```

`store.HailMetrics(ctx, since)` runs one query over `hails WHERE created_at >= ? AND decided_at IS NOT NULL`, grouped by `original_decided_by`, with the two percentiles computed in Go over the fetched rows; a week's worth of hails is small enough that an in-SQLite percentile isn't worth the SQL. "Auto-resolved share" is `(ByOriginalDecider[policy] + ByOriginalDecider[command]) / Decided`; "captain overrides" is `Countermanded / Decided`. CLI: `bmus hails metrics [--since <duration>]`, default `7d`, matching the exit criterion's "a week of use," printed as a small table. RPC: `hails.metrics`. This is read-only and additive; it needs nothing from the console beyond, optionally, a panel later, which this plan doesn't add, the exit criterion asks that the rates be reported, not that the console show them.

### 10. Tracker interface (#54)

#54's own issue body already specifies the `Tracker` interface, the adapter registry, `orders.source`, and the new `tracker_request`/reply pair. This plan's only addition is where it slots into Regulations: a tracker write (`create`, `comment`, `close`) becomes a hail exactly like `order_split`, with a category per op (`tracker_create`, `tracker_comment`, `tracker_close`), so the captain can set each one's route independently in `regs.yaml` rather than the issue's open "which ops are captain-only" question being hardcoded. The default `regs.yaml` answers that question conservatively: `tracker_create` and `tracker_close` under `captain_only`, `tracker_comment` left to the default Command-routed path. #54 should be picked up alongside §2 to §4 of this plan, the same hail and Regulations machinery, not before or after them.

## Assumptions

- The `command` division is reserved by convention (`DivisionCommand = "command"`), not enforced as a disallowed name for any other crew member; nothing stops a captain from naming a division `command` for an unrelated purpose, and nothing here checks for that. Worth revisiting if it ever causes confusion.
- `consultTimeout` (10m), `--hail-park-after` (15m) and the default `regs.yaml`'s specific rules are starting points named in D4 and the initial plan's illustrative config, not measured values. The first week of real use, §9's metrics, is also the first chance to tune them.
- `regs.CheckAnswer`'s re-check runs only on Command's own proposed option or answer, not on a hail's full option list up front: a hail already classified `RouteCommand` whose options are all captain-only still goes to Command first, who then has every option rejected and nowhere to go but escalate. That is the intended fallback, not a bug, but it costs one wasted consult round trip before such a hail reaches the captain. A later pass could classify "every option captain-only" straight to `RouteCaptain`.
- A consult runs as its own `query()` alongside whatever order Command is running, in the same beam. Command's API usage can therefore double while both lanes are busy.
- Command's `consult` lane assumes the sdk harness; holodeck's scripted stand-in (§Verification item 6) is for CI determinism, not a second real implementation. A Command crew member provisioned with `--harness echo` or `holodeck` outside tests always escalates, by design (§5).

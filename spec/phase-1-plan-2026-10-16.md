# BMUS Phase 1 — One crew member, end to end

## Context

`spec/initial-plan-2026-10-16.md` (§9) scopes Phase 1 as: a `bmus` binary with DBOS on SQLite; a `tsh` transporter; combadge v0 (Agent SDK harness, outbox, protocol, `beamctl` service); crew-tour and mission workflows; directed orders; hails straight to the captain via CLI; the captain's log; a holodeck transporter and harness. Exit: kill the bridge mid-mission and restart it and the mission completes; kill the beam and the crew member lands in sickbay with a checkpoint; the same two scenarios pass in holodeck CI.

The repository (`~/Workspace/bmus`) is currently empty except for `spec/` and `AGENTS.md` — no `go.mod`, no commits, no GitHub remote. This plan starts from nothing and produces a working single-crew bridge.

Two things in the spec need pinning down before implementation, resolved below with reasoning (not left to the implementer):

1. **Checkpoint source for the sickbay exit criterion.** §9 assigns periodic/TTL-driven checkpointing (watch change, re-energize-with-resume) to Phase 2. The only Phase-1-scoped checkpoint trigger left in §4/D5 is the agent calling `request_handover` — one of the three in-process tools §4/D4 already lists for Phase 1. So the "sickbay with a checkpoint" scenario means: the agent (or the holodeck script standing in for it) calls `request_handover` at least once before the beam dies; the bridge has that checkpoint in the cargo bay when sickbay is declared. No automatic/periodic checkpointing is built in Phase 1.
2. **Hail workflow.** §5's workflow table shows a dedicated `hail/<id>` workflow, but that machinery (Regulations, Command routing, countermand) is explicitly Phase 3. Phase 1's own deliverable list only names "crew-tour and mission workflows." So Phase 1 handles a hail as an inline `Recv`/`Send` round trip inside the Mission workflow, addressed straight to the captain. Phase 3 extracts this into the standalone Hail workflow once Command exists — no code written now needs to anticipate that split.

One correction to the spec's shelled-out syntax: §4/D3 writes `tsh beams exec <beam> -- combadge attach --since <seq>`. The real `tsh beams` command form (confirmed against `https://goteleport.com/docs/beams`) takes the command directly, no `--` separator: `tsh beams exec <name> <cmd> [args...]`. Every step below uses the real form.

## Approach

### 1. Repo scaffold and domain store

- `go mod init github.com/tscolari/bmus` (no GitHub repo exists yet for this project; cheap to `go mod edit -module` later if it lands elsewhere). Target the installed toolchain, `go 1.26`.
- `internal/store/schema.sql` (embedded via `//go:embed`): `CREATE TABLE IF NOT EXISTS` for exactly the six tables in spec §7 — `crew`, `beams`, `orders`, `hails`, `checkpoints`, `log`, `inbox` — with the columns §7 lists for each (no new columns, no new tables; Phase 2's dispatcher reuses `priority`/`division` columns created now but unused by Phase 1 logic).
  - `orders.id` and `hails.id` are `TEXT PRIMARY KEY`. Both are application-generated inside the same insert transaction: `fmt.Sprintf("ORD-%04d", n)` / `fmt.Sprintf("H-%04d", n)` where `n` is `(SELECT COUNT(*) FROM orders) + 1` (resp. `hails`) read and inserted in one `*sql.Tx`. Safe because the bridge is the only writer (D1).
  - `crew.id` is a human-readable slug (e.g. `sorell`), supplied by the operator at `bmus crew add`, not generated.
- `internal/store/store.go`: opens its own `*sql.DB` against the **same file** DBOS uses (`~/.bmus/bridge.db`), via the `sqlite` driver name that `modernc.org/sqlite` self-registers (the same driver DBOS's blank import below registers under). DSN: the plain file path, not the `sqlite:` URL DBOS uses — `database/sql`'s own `Open` doesn't take DBOS's URL scheme. Set `_pragma=busy_timeout(5000)` and `_pragma=journal_mode(WAL)` on the DSN query string. One exported method per table per operation needed later (`InsertCrew`, `GetCrew`, `ClaimOldestDirectedOrder(crewID)`, `InsertHail`, `MarkHailDecided`, `InsertCheckpoint`, `AppendLog`, `InsertInboxSeq`/`SeenInbox`, etc.) — no generic query builder, this is a handful of tables.
- Process lock: `~/.bmus/bridge.lock`, taken with `syscall.Flock` (`LOCK_EX|LOCK_NB`) at startup; `bmus bridge run` exits with a clear error if already held, per D1 ("single-writer").

### 2. DBOS wiring

- Blank-import `_ "github.com/dbos-inc/dbos-transact-golang/dbos/driver/sqlite"` in `internal/bridge/daemon.go` to register the SQLite backend.
- `dbos.NewContext(ctx, dbos.Config{DatabaseURL: "sqlite:" + absPath("~/.bmus/bridge.db"), AppName: "bmus"})`. The `sqlite:` scheme with a single leading slash before an absolute path is the form the driver's `DetectDialect`/`SqliteDSN` parse (verified against `dbos-transact-golang`'s own DSN tests); do **not** use `sqlite://`.
- Register `crewTourWorkflow` and `missionWorkflow` (§3 below) with `dbos.RegisterWorkflow` before `dbos.Launch`.
- `dbos.Launch(ctx)`; `defer dbos.Shutdown(ctx, 10*time.Second)` on graceful SIGINT/SIGTERM (via `signal.NotifyContext`). On an ungraceful kill (`kill -9`), nothing runs — recovery is handled entirely by DBOS on the next `Launch`: per DBOS's own docs ("Recovery On A Single Server"), *every* restart of a single-process DBOS app automatically resumes all `PENDING` workflows, with no explicit recovery call needed. This is the mechanism the "kill the bridge mid-mission, restart it, mission completes" exit criterion relies on — do not add a manual recovery step, and do not change `AppName`/`ApplicationVersion` between the kill and the restart in the verification run, or DBOS will treat the resumed workflow as a different app version and skip it.
- At startup, after `Launch`, for every `crew` row with `status != 'dismissed'`, re-`RunWorkflow` `crewTourWorkflow` with `dbos.WithWorkflowID("crew/"+id+"/tour/"+tourNo)` — this is a no-op if that workflow ID is already `PENDING` (idempotent start), and is what re-attaches to a crew member whose tour was already running before a restart.

### 3. Wire protocol and shared schema

- `protocol/messages.schema.json`: JSON Schema (2020-12) with one `oneOf` branch per message `type` from spec §6 — `hello`, `heartbeat`, `progress`, `hail`, `checkpoint_ready`, `report`, `error` (beam→bridge) and `ack`, `order`, `answer`, `checkpoint`, `stand_down`, `recall`, `belay` (bridge→beam). `consult_reply`/`consult` from §6 are Command-lane-only (Phase 3) — include their shapes in the schema now (cheap, and §12 already commits `protocol/` to being the one shared source of truth) but neither side needs to emit or handle them yet.
- `protocol/golden/*.json`: one example payload per message type, taken from §6's example and reasonable Phase-1 fixtures.
- Go side: hand-written structs in `internal/comms/protocol.go` (`type Message struct { V int; Seq uint64; Crew, Order string; Type string; TS time.Time; Body json.RawMessage }` plus a typed `Body` struct per `Type`). A test (`internal/comms/protocol_golden_test.go`) loads every file in `protocol/golden/`, validates it against `messages.schema.json` with `github.com/santhosh-tekuri/jsonschema/v6`, and round-trips it through `json.Unmarshal`/`json.Marshal` into the Go struct, failing if any golden fixture fails either check.
- TS side: `combadge/src/protocol.ts` hand-written types mirroring the Go structs; `combadge/test/protocol.golden.test.ts` validates the same `protocol/golden/*.json` files against the schema with `ajv` and parses them with the TS types. Both suites read the *same* `protocol/` directory — that's the shared-source-of-truth property spec §12 asks for.

### 4. Transporter abstraction

- `internal/transporter/transporter.go`: 
  ```go
  type Beam struct { Alias string; ExpiresAt time.Time }
  type Provider interface {
      Create(ctx context.Context) (Beam, error)
      Exec(ctx context.Context, beam Beam, name string, args ...string) (Session, error)
      Probe(ctx context.Context, beam Beam) (healthy bool, err error)
      Remove(ctx context.Context, beam Beam) error
  }
  type Session interface {
      io.WriteCloser          // write to the remote process's stdin
      Stdout() io.Reader       // read the remote process's stdout
      Wait() error             // block until the process/session ends
  }
  ```
- `internal/transporter/tsh.go`: `Create` runs `tsh beams add --no-console --format=json`, parses the JSON for the alias/expiry. `Exec` runs `tsh beams exec <alias> <name> <args...>` as an `*exec.Cmd` with piped stdin/stdout, returning that as the `Session`. `Probe` first checks `tsh beams ls --format=json` for the alias (gone ⇒ unhealthy); if present, runs `tsh beams exec <alias> true` with a 5s timeout (fails/times out ⇒ unhealthy). `Remove` runs `tsh beams rm <alias>`.
- `internal/transporter/holodeck.go`: `Create` is a no-op that mints a synthetic alias (`holodeck-<pid>-<n>`) and a 24h-out expiry; no VM. `Exec` with `name == "combadge"` and the `serve` subcommand starts `node dist/combadge.js serve --socket ~/.bmus/holodeck/<alias>.sock` as a detached `*exec.Cmd` (own process group, *not* killed if the bridge dies — this is what lets the beam "survive" a bridge crash in the restart-recovery test); `Exec` with `attach` starts `node dist/combadge.js attach --socket ~/.bmus/holodeck/<alias>.sock --since <seq>` as a plain `*exec.Cmd` whose stdin/stdout are the `Session` (this is the half that *should* die with the pump — it's just a relay). `Probe` checks the serve process is still alive (`syscall.Kill(pid, 0)`). `Remove` kills the serve process. A separate `Kill(alias)` helper (not on the `Provider` interface — only the holodeck test harness calls it) `SIGKILL`s the serve process to simulate the beam dying, used by the sickbay test.
- Which `Provider` the daemon uses is a startup flag: `bmus bridge run --transporter=tsh|holodeck` (holodeck is also the default for `go test`).

### 5. Combadge (TypeScript, `combadge/`)

- `npm init`, deps: `@anthropic-ai/claude-agent-sdk`, `zod`, dev dep `esbuild`, `typescript`, `vitest` (test runner, consistent with the rest of the TS tooling — no existing JS convention in this repo to match).
- `combadge/src/serve.ts` — the long-running process. Owns:
  - A local outbox: an append-only NDJSON file (`~/combadge/outbox.ndjson` inside the beam) of every beam→bridge message, each tagged with a per-process monotonic `seq`. `serve` keeps writing here even with no `attach` session connected (D3's "agent keeps working while bridge is away").
  - A Unix socket server (path from `--socket`). Each `attach` connection sends `{"since": N}` first; `serve` replays outbox entries with `seq > N`, then streams new ones live, and relays anything written to the socket back into the harness's inbound command handler (`ack`/`order`/`answer`/`checkpoint`/`stand_down`/`recall`/`belay`).
  - The harness (§ below), selected by `--harness=sdk|holodeck` (default `sdk`).
  - A heartbeat timer: every 10s, emit a `heartbeat` message with basic health (disk/mem via `os.freemem`/`statfs` equivalents).
- `combadge/src/attach.ts` — the short-lived relay the pump launches once per connection. Dials `--socket`, sends `{"since": <seq>}`, then pumps bytes bidirectionally between the socket and its own stdin/stdout until EOF or the socket closes (reconnect is the pump's job, not `attach`'s).
- `combadge/src/harness/types.ts`: 
  ```ts
  interface Harness {
    run(order: OrderBody, emit: (m: OutboundBody) => void, onInbound: (fn: (m: InboundBody) => void) => void): Promise<ReportBody>;
  }
  ```
- `combadge/src/harness/sdk.ts` (Phase 1's real harness): wraps `query()` from `@anthropic-ai/claude-agent-sdk`.
  - `permissionMode: "bypassPermissions"` (matches the beam's own fully-trusted-identity model per the Beams long-running-agents guide's own demo, which uses `--dangerously-skip-permissions`).
  - `hooks: { PreToolUse: [{ matcher: "Bash", hooks: [gitPushPolicy] }] }` where `gitPushPolicy` regex-matches the `command` field: a `git push` containing `--force`/`-f`/`+` refspec ⇒ `{hookSpecificOutput: {hookEventName: "PreToolUse", permissionDecision: "deny", permissionDecisionReason: "force-push is blocked"}}`; a plain `git push` ⇒ `{hookSpecificOutput: {hookEventName: "PreToolUse", permissionDecision: "ask"}}` (routes to `canUseTool` even under `bypassPermissions`, since hooks are evaluated before the permission-mode step); everything else ⇒ `{}` (falls through to `bypassPermissions`, i.e. runs). This is D4's "deny force-push, route plain git push to a hail" made concrete.
  - `canUseTool`: for `AskUserQuestion` and for the hook-routed `ask` on `Bash`, build a `hail` body (`category` is `"clarifying_question"` or `"tool_approval"`), call `emit({type:"hail", body})`, `await` the matching `answer` delivered through `onInbound`, and return `{behavior:"allow", updatedInput: input}` or `{behavior:"deny", message: answer.decision}` depending on what the captain picked. Phase 1 only implements the "hold" wait mode (await indefinitely inside the callback) — no `defer`/park, per the plan's resolved scope above.
  - In-process tools via `tool()` + `createSdkMcpServer({name:"combadge", tools:[progress, report, requestHandover]})`, passed through `mcpServers` and listed in `allowedTools` as `mcp__combadge__progress` etc. so they never prompt:
    - `progress(pct: number, note: string)` → `emit({type:"progress", body:{pct, note}})`.
    - `report(summary: string, artifacts: string[])` → stashes the final report; the harness returns it as the `ReportBody` once the SDK's `query()` loop ends.
    - `request_handover(note: string)` → runs `git bundle create <tmp>/work.bundle <base_ref>..HEAD` in the order's workdir, copies the current Claude session's transcript file (located via the session id captured from the SDK's result message, under `~/.claude/projects/<encoded-cwd>/<id>.jsonl` per the SDK's own session-storage layout) to `<tmp>/transcript.jsonl`, writes `note` to `<tmp>/handover.md`, and `emit({type:"checkpoint_ready", body:{bundle_path, transcript_path, handover_path}})`.
- `combadge/src/harness/holodeck.ts` (scripted stand-in, D10): takes a `--script` path (JSON array of steps: `{"at_pct":10,"progress":"..."}`, `{"at_pct":40,"hail":{...}}`, `{"at_pct":60,"request_handover":"mid-mission checkpoint"}`, `{"at_pct":100,"report":{...}}` or `{"crash":137}`). Walks the script, calling the same `emit`/`onInbound` surface a real harness would, so the comms/protocol code under test is identical to the SDK path. Default fixture script used by the CI tests below includes the `request_handover` step specifically so the sickbay-with-checkpoint scenario has something to find.
- `combadge/esbuild.config.mjs`: bundles `src/serve.ts` and `src/attach.ts` (two entry points) into `dist/combadge.js` as a single CommonJS file with all `node_modules` inlined (`bundle: true, platform: "node", external: []`), so a beam needs nothing beyond the Node already preinstalled on the default beam image — no custom crew image, no `npm install` on the beam. `dist/combadge.js` dispatches on `process.argv[2]` (`serve`/`attach`) to pick the entry.

### 6. Comms pump

- `internal/comms/pump.go`: one `Pump` per live crew member, owned by the daemon in a `map[string]*Pump` registry (`internal/bridge/daemon.go`), guarded by a mutex.
  - Reconnect loop: `transporter.Exec(ctx, beam, "combadge", "attach", "--since", strconv.FormatUint(lastAcked, 10))` (tsh) or `("combadge", "attach", "--socket", sockPath, "--since", ...)` (holodeck); on the session's `Wait()` returning (EOF, SSH drop, process exit), back off (1s, 2s, 4s... capped at 30s) and retry, unless the pump has been told to stop (crew dismissed/beam removed).
  - Inbound: decode NDJSON lines from `Session.Stdout()` into `comms.Message`; dedup via `store.SeenInbox(crewID, seq)` (the `inbox` table) — if already seen, write the `ack` anyway (idempotent at-least-once) and skip forwarding; otherwise `store.InsertInboxSeq(...)`, write `ack`, and dispatch by `Type`:
    - `heartbeat` → update an in-memory `lastHeartbeatAt[crewID]`, used by the sickbay check below.
    - `progress` → `store.AppendLog(...)` directly (not routed through a workflow — matches D3: "progress... goes straight to the log, not into workflows").
    - `hail`, `checkpoint_ready`, `report`, `error` → `dbos.Send(dbosCtx, "order/"+msg.Order, msg.Body, "from-crew")`.
  - Outbound: `pump.Send(cmd comms.Command) error` assigns a command ID, marshals, writes a line to `Session`'s stdin. Called from Mission/CrewTour workflow steps via the registry lookup (`daemon.Pumps[crewID]`), never directly from workflow code (I/O must be in a step). Phase 1 does not persist/redeliver unacked outbound commands across a pump reconnect — if a command is lost mid-flight, the operator re-runs the CLI command that issued it (e.g. re-run `bmus hails answer`). This is an accepted scope boundary; Phase 2's reconcile work can add redelivery.
  - Sickbay check: a ticker every 10s per pump; if `now - lastHeartbeatAt[crewID] > 30s` (3 missed beats) and the crew isn't already `sickbay`, call `transporter.Probe(ctx, beam)`. Unhealthy or beam gone ⇒ `dbos.Send(dbosCtx, "crew/"+crewID+"/tour/"+tourNo, CrewSignal{Kind:"heartbeat_missed"}, "crew-events")`. Healthy ⇒ log a warning and keep waiting (treated as a transient comms hiccup, not sickbay).

### 7. CrewTour workflow

`internal/bridge/crewtour.go`, ID `crew/<id>/tour/<n>`:

```go
func crewTourWorkflow(ctx dbos.Context, in CrewTourInput) (CrewTourResult, error) {
    beam, err := dbos.RunAsStep(ctx, func(c context.Context) (transporter.Beam, error) { return provisionAndStartCombadge(c, in.CrewID) })
    // provisionAndStartCombadge: Create() beam, mkdir, scp dist/combadge.js (tsh) or just reference dist/combadge.js on disk (holodeck),
    // Exec("combadge","serve",...) via beamctl for tsh ("tsh beams exec <alias> beamctl start --name=combadge -- node .../combadge.js serve --socket ...")
    // or directly for holodeck. Registers the Pump in daemon.Pumps[in.CrewID] and starts its reconnect loop.
    dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) { return struct{}{}, store.SetCrewStatus(in.CrewID, "on_deck", beam.Alias) })
    for {
        orderID, found, err := dbos.RunAsStep(ctx, func(c context.Context) (string, bool, error) { return store.ClaimOldestDirectedOrder(in.CrewID) })
        if !found {
            sig, err := dbos.Recv[CrewSignal](ctx, "crew-events", 24*time.Hour)
            if err (timeout) { continue } // loop back to the claim check
            switch sig.Kind {
            case "order_assigned": continue // loop back to claim it
            case "heartbeat_missed": 
                dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) { return struct{}{}, store.SetCrewStatus(in.CrewID, "sickbay", beam.Alias) })
                return CrewTourResult{Ended:"sickbay"}, nil // Phase 1: sickbay is terminal for the tour; re-energize is Phase 2
            }
            continue
        }
        dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) { return struct{}{}, store.SetCrewStatus(in.CrewID, "away", beam.Alias) })
        dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) { return struct{}{}, pump.Send(order{...}) }) // bridge→beam "order" command
        handle, err := dbos.RunWorkflow(ctx, missionWorkflow, MissionInput{OrderID: orderID, CrewID: in.CrewID}, dbos.WithWorkflowID("order/"+orderID))
        result, err := handle.GetResult() // blocks until the mission ends; errors propagate but don't kill the tour
        dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) { return struct{}{}, store.SetCrewStatus(in.CrewID, "on_deck", beam.Alias) })
    }
}
```

- `CrewSignal{Kind string; OrderID string}` sent on topic `"crew-events"` from two places outside the workflow: the daemon's order-create RPC handler (`Kind:"order_assigned"`, only if the crew is currently `on_deck` — otherwise it just leaves the row in the table for the next claim-check) and the pump's sickbay check (`Kind:"heartbeat_missed"`).
- Phase 1 deliberately does not implement watch-change (TTL-driven rotation) or re-energize-from-sickbay — both are Phase 2. A `sickbay` tour simply ends; the crew member stays `sickbay` in the `crew` table until an operator intervenes (out of scope for Phase 1's CLI).

### 8. Mission workflow

`internal/bridge/mission.go`, ID `order/<id>`:

```go
func missionWorkflow(ctx dbos.Context, in MissionInput) (MissionResult, error) {
    for {
        msg, err := dbos.Recv[comms.CrewMessage](ctx, "from-crew", 24*time.Hour)
        if timeout { dbos.RunAsStep(ctx, markOrderFailed("no activity from crew for 24h")); return MissionResult{}, fmt.Errorf("mission %s stalled", in.OrderID) }
        switch msg.Type {
        case "progress": // already logged by the pump directly; nothing to do here
        case "hail":
            hailID, err := dbos.RunAsStep(ctx, func(c context.Context) (string, error) { return store.InsertHail(in.OrderID, in.CrewID, msg.Body) }) // route="captain", status="open"
            answer, err := dbos.Recv[comms.HailAnswer](ctx, "from-hail", 24*time.Hour)
            if timeout { dbos.RunAsStep(ctx, markHailTimedOut(hailID)); return MissionResult{}, fmt.Errorf("hail %s timed out", hailID) }
            dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) { return struct{}{}, pump.Send(answerCmd(hailID, answer)) })
            dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) { return struct{}{}, store.MarkHailDecided(hailID, "captain", answer) })
        case "checkpoint_ready":
            dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) {
                return struct{}{}, pullAndRecordCheckpoint(in.OrderID, msg.Body) // scp bundle/transcript/handover into ~/.bmus/cargo/<order>/<seq>/, INSERT INTO checkpoints
            })
        case "report":
            dbos.RunAsStep(ctx, func(c context.Context) (struct{}, error) { return struct{}{}, store.MarkOrderDone(in.OrderID, msg.Body) })
            return MissionResult{Status:"done", Report: msg.Body}, nil
        case "error":
            dbos.RunAsStep(ctx, markOrderFailed(msg.Body.Reason))
            return MissionResult{}, fmt.Errorf("crew error: %s", msg.Body.Reason)
        }
    }
}
```

- The CLI's `bmus hails answer <hail-id> ...` RPC handler resolves `hail-id → order_id` from the `hails` table and does `dbos.Send(dbosCtx, "order/"+orderID, HailAnswer{...}, "from-hail")` directly (not from inside a workflow — `Send` only needs the context).
- `pullAndRecordCheckpoint` uses `transporter.Exec`-equivalent `scp`: for tsh, `tsh beams scp <alias>:<bundle_path> ~/.bmus/cargo/<order>/<seq>/work.bundle` (and same for transcript/handover); for holodeck, the "beam" is a local process, so this is a plain file copy from the paths `request_handover` already wrote on the local filesystem. This is the mechanism the sickbay-with-checkpoint exit criterion needs: a checkpoint produced via `request_handover` lands in the cargo bay and a `checkpoints` row exists *before* the beam is killed.

### 9. CLI and local-socket RPC

- `internal/bridge/rpc.go`: Unix socket at `~/.bmus/bridge.sock`. One newline-delimited JSON request/response per connection: `{"cmd":"<name>","args":{...}}` → `{"ok":true,"result":{...}}` or `{"ok":false,"error":"..."}`. Commands: `crew.add`, `crew.list`, `order.create`, `order.list`, `hails.list`, `hails.answer`, `log.tail` (takes `{"since_id":N}`, returns new rows — the CLI's `--follow` loops this with a short sleep).
- `cmd/bmus/` (Cobra, the standard Go CLI framework — matches the "boring/standard" bar and is what a Go CLI with this many subcommands conventionally uses):
  - `bmus bridge run [--transporter=tsh|holodeck]` — runs the daemon in the foreground (§2); the operator supervises it (tmux/systemd/etc.), matching D1's "single Go binary" with no separate service-manager layer added in Phase 1.
  - `bmus crew add <id> --name <name> --rank <rank> --division <division> [--dossier <path>]` → `crew.add`.
  - `bmus crew list` → `crew.list`.
  - `bmus order create <order.yaml>` → parses a YAML file (`title`, `division`, `assignee`, `base_ref`, `budget_tokens`, `body`) and calls `order.create`.
  - `bmus order list` → `order.list`.
  - `bmus hails list` → `hails.list`.
  - `bmus hails answer <hail-id> --option <n>|--decision <text>` → `hails.answer`.
  - `bmus log tail [--follow]` → `log.tail`, polling every 500ms when `--follow` is set.

### 10. Captain's log

No separate mechanism: every `store.AppendLog(kind, crewID, orderID, text, payload)` call already threaded through steps 6–8 above (pump progress, order claimed/done/failed, hail opened/decided, crew status changes) **is** the captain's log — append-only by construction (no `UPDATE`/`DELETE` on the `log` table anywhere in the code). `bmus log tail` is the read path.

### 11. Holodeck CI test suite

`internal/bridge/holodeck_test.go` (Go `testing` + `testify/require`, `t.Context()` per house convention — never the ambient `ctx` unless genuinely shared):

- `TestMissionSurvivesBridgeRestart`: run the daemon as a real subprocess (`exec.Command` on the built `bmus` binary, not in-process — needed so it can actually be `SIGKILL`ed) with `--transporter=holodeck`, pointed at a temp `~/.bmus`. `crew add`, `order create` with a holodeck script that reaches ~50% progress and pauses (a script step with a deliberate multi-second delay). While paused, `SIGKILL` the daemon process. Start a new daemon subprocess against the same `bridge.db`. Assert (via `log tail` / `order list`) that the mission reaches `done` with the expected report, without re-running steps the script already passed (the holodeck script records which steps it executed, in a file outside `bridge.db`, so the test can assert no step replayed).
- `TestCrewSickbayOnBeamLoss`: same setup, holodeck script calls `request_handover` at ~50%, then the test calls the holodeck transporter's `Kill(alias)` directly (SIGKILL just the `combadge serve` process, bridge stays up). Assert: within ~35s, `crew list` shows `status=sickbay` for the crew, and a `checkpoints` row plus the three files it points at exist under `~/.bmus/cargo/<order>/`.
